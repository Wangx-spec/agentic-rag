# 优化复盘（通俗版）

> 这份文档讲人话：不堆术语，每个问题都按「发生了什么 → 为什么会这样 → 我怎么修的」讲清楚。  
> 适合面试前回顾，也适合直接对着它组织面试回答。

## 一、一句话总结

我做了一个「给企业知识库做智能问答」的系统。数据来源是github上的开源英文数据。我在做测试时发现：**系统看起来能跑，但真正问它问题时，答得并不好**。我一步步排查，发现背后藏着一个「偷偷失效」的 bug 和几个「设计上太死板」的地方，然后逐个修掉了。

整个过程最有价值的地方不是「最后分变高了」，而是**我怎么发现这些问题、怎么证明问题在哪、怎么验证修好了**——这才是面试官想听的。

**最终成绩单**（修完所有问题后，同一套 64 道英文企业知识库考题）：

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| 找对资料（Document Recall） | 48.37% | **66.20%** | +17.8pp |
| 答案覆盖全（Completeness） | 29.73% | **50.53%** | +20.8pp |
| 答案答对（Correctness） | 14.06% | **35.94%** | +21.9pp |
| 完全答对的题 | 9/64 | **23/64** | +14 题 |

## 二、我踩过的坑，逐个讲清楚

### 坑 1：我以为是"双保险"，其实有一个保险从来没生效过（最重要的发现）

**发生了什么**

我的问答系统在「找相关资料」这一步，本来设计了两条路同时找，最后合并结果，互相兜底：

- 一条路叫「按意思找」（向量检索 / embedding）：把文字变成一串数字，靠数字的相似度判断「这段内容和问题是不是一个意思」。
- 一条路叫「按关键词找」（BM25）：传统搜索引擎那套，看「问题和文档有没有相同的词」。

结果测试完我发现：**关键词这条路，从头到尾一次都没出过结果。**

**为什么会这样**

我去翻代码，发现一个很隐蔽的错误：系统每次启动时，有个「检查索引要不要重建」的判断写错了条件，导致它**每次都把辛苦建好的关键词索引清空重建**。于是关键词这条路的库永远是空的——它每次都在「空库」里找东西，当然什么都找不到，但因为它只是安静地返回「没找到」，不报错，所以谁都没发现。

打个比方：我雇了两个图书管理员，一个按「意思相近」找书、一个按「关键词」找书。结果关键词那个管理员的索引卡片，每天早上上班时都被保洁阿姨当废纸清掉了。他每天对着空柜子找书，找不着也不吭声，我还以为两个人都在干活。

**我怎么修的**

1. 给索引库加了一个「版本号标记」，只有版本真的变了才重建，而不是每次启动都重建。
2. 加了一个「体检」：每次启动时自动对比「数据库里登记了多少文档」和「关键词索引里实际有多少条」，对不上就立刻报警。

**这件事教给我什么**：一个「静默失效」的组件比「报错崩溃」更危险——报错至少你能看见。所以我现在特别重视给系统加「健康检查」，让它自己会喊「我不对劲」。

### 坑 2：关键词找得太"较真"，长问题几乎全军覆没

**发生了什么**

修好坑 1 之后我发现，就算关键词索引不空了，它对「很长的问题」也基本无效。

**为什么会这样**

原来关键词那条路的规则是：**问题里的每一个词，都必须同时出现在文档里**，才算命中（专业上叫「全部都要满足」）。

这规则对短问题（比如「旋转密钥」）没问题。但真实的提问往往是一大段话，比如「请说明 GPU 镜像构建流程中，签名凭证的两阶段轮换流程，以及如何安全切换和回滚」——这一句里几十个词，要求它们**全部同时**出现在同一段文档里，几乎不可能。结果就是：问题越长，越搜不到。

打个比方：你在一个框里用「与」连接了几十个条件去搜，条件越多，能满足的越少，最后常常是「一条都没有」。

**我怎么修的**

改成「先严格搜，搜不到就放宽」的两步走：

1. 先按「全部都要有」搜一次；
2. 如果结果太少（少于 3 条），就自动放宽成「有几个关键词命中就行」，再搜一次。

同时做了几件让关键词更聪明的清理：

- **去掉废话词**：「的、了、是、the、is、a」这类词没有区分度，搜之前先扔掉。
- **统一词形**：把「running」和「run」当成同一个词（英文叫词干提取），避免因为时态差异漏掉。
- **重点照顾编号和日期**：像「工单号 CONF-1234」「日期 2024-01-15」这种又少见又关键的信息，单独拎出来重点匹配——因为这类精确信息正是关键词搜索最擅长、而「按意思找」最容易丢的。

### 坑 3：找到了资料，但答案还是不对——问题出在"答题"环节

**发生了什么**

测出两个很反常的现象：

- 有一道题，资料明明\** 100% 找对了\*\*，模型却回答「我不知道」。
- 有一道题，要求列出「工单号 + 日期」等多个细节，结果它漏了工单号。

**为什么会这样**

我原来给模型的「答题指令」写得太保守了：我写的是「如果资料不够，就明确说明不知道」。本意是防止它瞎编，结果它变得**过度胆小**——资料其实够了，它一看「好像不是 100% 确定」，就选择说「我不知道」。

另外，我的指令没明确要求「把题目里提到的每一个细节都答全」，所以它回答时容易「抓大放小」，漏掉编号、日期这种小细节。

**我怎么修的**

重写了答题指令，核心三句话：

1. **数字、日期、编号、名称这类关键信息，必须照着原文抄，不能省略、不能自己改。**
2. **题目问了几个点，就答几个点，一个都不能漏。**
3. **信息不太全的时候，也要基于现有资料尽力答，不确定的地方单独标出来，而不是直接说「不知道」。**

### 坑 4：一套题目考得好，不代表换个问法还考得好

**发生了什么**

我在思考一个问题：现在用的这套测试题，会不会「碰巧」对我的系统比较友好？换个人、换个问法，系统还能不能顶住？

**为什么会这样**

我检查了题目本身，发现它们有个共同点：**句子又长、又满是专业词**，而且这些专业词几乎原样出现在文档里。这恰恰是「按关键词找」最舒服的情况。

但真实用户不是这样问的。真实用户会说大白话、会用同义词、甚至会中英文混着问。如果系统只在「术语密集」的题目上表现好，那这个分数是虚的。

**我怎么修的**

我做了一件事，把「泛化能力」（换个问法还能不能答对）也变成可以量化的指标：

1. 把原来的题，用 AI 改写成了三种变体：①大白话版（去掉术语）②关键词精简版 ③中文翻译版。
2. 正确答案（应该找到的文档）不变，只改问法。
3. 分别跑一遍，看「换个问法后，成绩掉了多少」。

掉得少 = 系统稳；掉得多 = 之前的分数是虚高，得回去补。

这件事的价值在于：**我不只相信一套题的成绩，我会主动去「刁难」自己的系统**。

### 坑 5：测试工具自己出了毛病，差点让我误判

**发生了什么**

有一次我跑完整套测试，结果出来「正确率 0%」，我差点以为系统废了。后来发现**根本不是系统的问题，是判分的脚本没配置好**——它缺了几个环境变量，出错时又「悄悄吞掉错误、把结果记成 0 分」。

**为什么会这样**

判分脚本是第三方开源的，它有个坏习惯：调用大模型打分失败时，不报错，而是静默重试、最后把这道题记成「答错」。所以我看到的「全 0 分」，是「判分环节全失败」伪装成的「系统全答错」。

**我怎么修的**

1. 给判分脚本加了「开机自检」：启动时先确认关键配置都在，缺了就立刻报错退出，不许它「带病工作」。
2. 让它在出错时把错误打印出来，而不是默默吞掉。

**这件事教给我什么**：**当你看到「全 0」或「全 100」这种极端结果，第一反应应该是怀疑测试工具本身**，而不是马上相信结论。

### 坑 6：测试跑着跑着，偶尔有一篇文档导入失败（小毛病，已处理）

**发生了什么**

今天全量导入 5000 多篇文档时，有一篇报错「请求超时」，失败了。

**为什么会这样**

调大模型接口时，偶尔会因为网络慢、服务端繁忙，超过我设的「最多等 60 秒」而失败。

**我怎么处理的**

1. 先查清楚了：这个失败**不会中断整个流程**，系统会自动跳过这一篇继续跑剩下的。
2. 又确认了：这一篇文档**不在任何一道考题的答案里**，所以不影响最终分数。
3. 顺手把「最多等 60 秒」改成可以配置的、默认放宽到 120 秒，以后这类偶发失败会少很多。

这件事也提醒我：批量任务要有「单条失败不影响整体」的容错设计，以及「失败要能被看见和统计」。

## 三、这些坑背后的三个大问题

把上面的坑归归类，其实就三个大问题：

| 问题    | 大白话                 | 对应的坑                  |
| ----- | ------------------- | --------------------- |
| ① 找不到 | 该搜出来的资料没搜出来         | 坑 1（索引失效）、坑 2（关键词太较真） |
| ② 答不全 | 资料找到了，但答案漏了、错了、或不敢答 | 坑 3                   |
| ③ 不可信 | 分数本身有问题，或分数会虚高      | 坑 4、坑 5               |

面试时我通常这样开场：「我把问题分成了『找得到』『答得全』『测得准』三类，然后分别去攻。」

## 四、我具体做了什么优化（清单版）

| 做了啥                     | 解决哪个问题 | 通俗解释                    |
| ----------------------- | ------ | ----------------------- |
| 修索引重建判断 + 加健康检查         | ① 找不到  | 让「按关键词找」这条路真正活过来，还会自己报警 |
| 搜索改成"先严后宽"              | ① 找不到  | 长问题不再全军覆没               |
| 去掉废话词、统一词形、重点照顾编号日期     | ① 找不到  | 关键词搜得更准                 |
| 换个说法再搜一次（query rewrite） | ① 找不到  | 一个问题问两遍，提高命中率           |
| 先让模型写个"假答案"再拿去搜（HyDE）   | ① 找不到  | 用答案的风格去搜，比用问题去搜更容易对上    |
| 重写答题指令（照抄细节、逐项答全、尽力不拒答） | ② 答不全  | 资料对了，答案也要答全             |
| 造"换个问法"的变体题 + 通道单独测     | ③ 不可信  | 主动刁难自己，测出真实水平           |
| 判分脚本加自检                 | ③ 不可信  | 不让测试工具带病工作              |
| 超时调优 + 容错               | 稳定性    | 偶发失败不中断，且能被看见           |

> 注：以上每一项我都做了「对照实验」——关掉某个功能跑一遍、开着再跑一遍，看分数到底涨没涨。不是「我感觉有用」，是「数据证明有用」。

## 五、给面试官的话术（通俗版）

### 场景 1：请介绍你的项目，以及你做了什么优化

> 「我做的是一个给企业知识库做智能问答的系统。做完第一版测试，我发现它『能跑但答得不好』。于是我做了一件事：不急着调参，先搞清楚『到底哪里不行』。
>
> 结果发现一个很有意思的问题——我本来设计了两种找资料的方式互相兜底，其中『关键词搜索』这条路，因为一个隐藏的判断条件写错了，导致它每次启动都被清空、一直空转。它不报错，只是安静地返回『没找到』，所以很长时间没人发现。这让我意识到，『静默失效』比『报错崩溃』更危险。
>
> 修好之后，我又针对『找到了资料但答案答不全』『换个问法就不行了』这些点逐个优化，每改一处都用对照实验验证收益。最后我不只把分数提上去了，还建立了一套『能自己报警、能抗住换问法』的测试体系。」

### 场景 2：你怎么证明你的优化真的有用？

> 「我不信『我改了所以变好了』。我每改一个功能，都会做对照实验：关掉它跑一遍、开着它再跑一遍，看分数差多少。
>
> 另外我还做了一个很多人会忽略的事：主动去『刁难』自己的系统。我把原来的测试题改写成三种问法——大白话版、精简关键词版、中文翻译版，正确答案不变，只换问法。如果换个问法分数就暴跌，说明我之前是『题目碰巧友好』，不是真本事。这套做法让我能区分『真提升』和『假繁荣』。」

### 场景 3：你遇到过最头疼的 bug 是什么？

> 「最头疼的是一个『不报错』的 bug。我的系统有两套找资料的机制，其中一套因为判断条件写错，每次启动都被清空，等于一直在空跑。它从不报错，就是默默返回『没找到』，所以测试一路都是绿的，谁都没发现它根本没工作。
>
> 最后是我发现分数有异常、一层层追下去，才发现这个『沉默的失效』。修好它之后，我专门给系统加了『健康检查』，让它每天早上自己体检：数据库里登记了多少文档、索引里实际有几条，对不上就报警。从那以后我就特别警惕那些『不吭声的故障』。」

### 场景 4：如果让你评价自己的系统，它现在怎么样？

> 「我会诚实地说：工程链路已经比较完整了，但『回答质量』还在爬坡。具体讲，『按关键词找』和『按意思找』这两条路现在都真正在工作了，长问题也不会搜不到；但『多个文档要拼起来回答』这类复杂题，还是短板。我清楚它的边界在哪，也有一份排好优先级的改进清单，而不是盲目说『下一步换个更贵的模型』。」
