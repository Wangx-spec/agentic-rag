# M6 加 Reranker 可行性评估

> 2026-09-19。背景：era-2 r06 指标 recall 66.20% / correctness 35.94%，归因分析（见
> 《2026-09-19-era2指标归因分析-为何不到90》）定位瓶颈 B 为"每题平均 3.09 个无效文档混入
> 生成上下文 + 语料故意埋数字冲突干扰"。本文评估在 M6 阶段加入 reranker 的可行性。
> **结论：可行，推荐做。全部硬指标已实测，工作量 0.5-1 天，成本趋近于零。**

## 一、可行性验证（全部实测，2026-09-19）

### 1.1 模型与 API 可用性 ✅

硅基流动提供 6 个 rerank 模型，与现有 `LLM_API_KEY` 共用同一 key，零额外账号配置：

| 模型 | 说明 |
|---|---|
| **BAAI/bge-reranker-v2-m3** | **推荐**。多语言、轻量、8K 上下文 |
| Pro/BAAI/bge-reranker-v2-m3 | 付费加速版（¥0.07/M tokens） |
| Qwen/Qwen3-Reranker-0.6B / 4B / 8B | 更新的系列，可作备选 |
| Qwen/Qwen3-VL-Reranker-8B | 多模态版（本项目用不上） |

API 端点 `POST /v1/rerank`，**Cohere 兼容协议**（query + documents + top_n → results[{index, relevance_score}]），
返回已按分数降序排列，`return_documents=false` 节省带宽。

### 1.2 区分度 ✅（这是核心）

用评测语料真实文档实测（20 个候选，1 个 gold + 19 个随机干扰）：

- gold 文档排 **第 1**，分数 **0.344**；第 2 名仅 0.073（4.7 倍差距）
- 小规模测试中 gold 0.9996 vs 干扰项 ~1e-5（4 个数量级差距）

对比现状：RRF 分数只做粗排，invalid_extra 3.09 说明前 5 名里混了大量噪声。
Cross-Encoder 精排的分数区分度正是"把冲突陷阱文档踢出 top-N"所需要的。

### 1.3 延迟 ✅

| 场景 | 实测 |
|---|---|
| 3 候选 × 短文本 | 0.16s |
| **20 候选 × 2000 字符（拟接入规模）** | **0.47s，10.9K tokens/次** |

评测全量（64 题 × 3 路查询[原始+改写+HyDE] × 20 候选）≈ 2.1M tokens：
基础版**免费**，Pro 版约 ¥0.15。延迟影响：每次检索 +0.5s，对评测无感，生产可配置开关。

### 1.4 与现有架构的契合度 ✅

接入点唯一且清晰：`HybridRetriever.searchAndMerge()` 中 RRF 融合之后、截断 finalTopN 之前：

```
现状：  BM25 top10 + Vector top10 → RRF 融合 → 取 top5 → 送生成
改后：  BM25 top10 + Vector top10 → RRF 融合 → 取 top20 → rerank 精排 → 取 top5-8 → 送生成
```

- `SearchKnowledgeBaseTool`（Agent 模式）走同一 `HybridRetriever`，**rerank 对 r07 agent 链路自动生效**
- 与 rewriter/HyDE 正交：多路查询各自 rerank 后再融合，互不干扰
- fail-open 设计：rerank 调用失败（超时/限流）时回退 RRF 原序并 WARN，与现有 rewriter/HyDE 的降级策略一致

## 二、改动清单（预估 0.5-1 天）

| 改动 | 内容 |
|---|---|
| `RagProperties` | 新增 `Rerank` 配置组：`enabled`(默认 false) / `model` / `candidateSize`(默认 20) / `finalTopN` 联动 |
| `RerankClient`（新增） | 参照 `EmbeddingClient`：重试、超时、fail-open；Cohere 协议解析 |
| `HybridRetriever` | `searchAndMerge` 插入 rerank 分支（约 20 行） |
| `application.yaml` | `rag.retrieval.rerank.*` + 环境变量 `RAG_RETRIEVAL_RERANK_ENABLED` |
| 单测 | mock rerank 响应的排序正确性 + 失败回退 RRF 序 + 开关关闭走原路径 |
| 消融轮 | r08：r06 配置 + rerank（+ 可选 finalTopN 5→8 对比） |

## 三、预期收益与边界（诚实评估）

**能解决的（瓶颈 B）**：
- invalid extra 3.09 → 预期降到 1 以下，冲突陷阱文档（"48h vs 3 business days"类）被踢出上下文
- 受益题型：constrained（recall 81.8 但 corr 仅 18.2，纯被噪声拖死）、basic 的干扰型失分
- correctness 预期提升 5-10pp（对照瓶颈 B 涉及约 25% 题量估算）

**不能解决的**：
- 瓶颈 C（13 题零召回）：rerank 只能重排"已召回"的候选，gold 不在 top-20 里就救不回
- 瓶颈 A（completeness 多文档上限）：需配合 finalTopN 8-10 才能部分缓解
- 瓶颈 D（生成模型档位）：与检索无关

## 四、风险与对策

| 风险 | 对策 |
|---|---|
| chunk 级 rerank 对"文档级正确"的偏差（gold 的非关键 chunk 可能被压分） | 候选集按文档分组去重后 rerank；或 chunk rerank + 文档级 max 聚合 |
| 长查询（32 token 中位数）与 HyDE 假设文档的匹配度 | rerank 用原始 query，不用 HyDE 变体 |
| 免费版限流 | 实测单次 0.5s、评测仅 192 次调用，不会触发；生产可切 Pro |

## 五、优先级结论（r07 数据出来后的最终结论）

r07（AGENT 模式）实测：recall 75.22%（+9.0pp，多文档结构天花板被打破），但 **invalid extra 3.09 → 10.27（×3.3）**——
agent 多轮检索召回的文档更多也更脏，累积 sources 无剪枝直接暴露给生成端。

**结论：reranker 从"可选优化"升级为"必做前置"——没有精排就没有可用的 agent 检索。**

推荐落地顺序（合并为一条改造线，合计 1.5-2 天）：
1. **reranker 先行**（0.5-1 天）：`HybridRetriever` RRF 后 top-20 → rerank → top-N。RAG 模式立即受益
   （invalid extra 3.09 → 预期 <1），并作为 agent 模式的基础设施；
2. **AgentLoop 终答修复**（r07b 前置，0.5 天）：终答兜底检测 `<tool_call>` 泄漏 → 用累积 sources
   （去重 + rerank 剪枝到 top 5-8）走 RAG prompt 合成终答——"agentic 检索 + reranker 精排 + RAG 合成"
   三件套即榜首系统（OpenClaw / Omni）的架构形态；
3. **r07b 重跑**验证：预期 recall ~75 保持 + correctness 40+（超 r06 的 35.94）。
