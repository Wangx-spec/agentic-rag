# M6 测试综合报告：从 14% 到 43.75% 的完整评测记录

> 2026-09-21。汇总 M6 阶段（9 月 16 日 - 9 月 21 日）全部评测工作：
> 11 轮正式测试（r01-r06、r07、r08、r07b/c/d）+ 3 轮泛化性变体测试（v1-v3），
> 每轮 64 题，累计约 900 次作答与判分。本文回答五个问题：
> 数据从哪来、测了什么、踩了什么坑、结果如何、说明了什么。

---

## 一、测试的数据来源

### 1.1 测试集：EnterpriseRAG-Bench

用的是 Onyx（开源企业搜索公司）公开的测试集 **EnterpriseRAG-Bench**。它不是那种"文档里明明写着答案、换个问法就问出来"的简单题库，而是专门设计来为难检索问答系统的：

- **语料**：5187 篇企业 Wiki 文档（模拟一家虚构公司的内部知识库，内容涵盖运维手册、值班记录、故障复盘等）。语料里**故意埋了三种陷阱**：内容互相矛盾的近重复文档（比如一篇说"48 小时"，另一篇说"3 个工作日"）、故意放错位置的文档（占 8%）、没有营养的水帖。
- **题目**：我们选了其中的 confluence 子集，共 64 道题，分 8 种类型——有直接问事实的，有要求换种说法也能听懂的，有要求把散落在多篇文档里的信息拼全的，还有专门考察抗干扰能力的。
- **标准答案**：每道题都标注了"答案应该来自哪几篇文档"（gold 文档），这是计算检索准确率的依据。

### 1.2 判分方式：官方脚本 + 大模型裁判

判分不用我们自己写的规则，而是用测试集官方提供的 Python 脚本，由大模型（GLM-5.3，通过硅基流动 API 调用）当裁判，对每道题打出四个指标：

| 指标 | 含义 | 通俗解释 |
|---|---|---|
| Document Recall（文档召回率） | 该找到的文档找到了百分之几 | 检索准不准 |
| Completeness（完整度） | 答案覆盖了标准答案要点的百分之几 | 答得全不全 |
| Correctness（正确率） | 答案内容对不对（二元判定，数字必须完全一致） | 答得对不对 |
| Invalid Extra（无效引用数） | 引用的文档里有多少篇是不相干的 | 检索干不干净 |

前三个越高越好，最后一个越低越好。

### 1.3 被测系统

本项目自研的检索问答系统，核心链路是：**BM25 关键词检索 + 向量语义检索 → RRF 融合排序 → （可选）rerank 精排 → 大模型生成答案**。另有一种 Agent 模式：大模型自主决定"搜什么、搜几次、什么时候作答"的多轮循环。全部测试在同一台机器、同一份语料、同一个裁判模型下完成，每轮测试只改一个变量，保证对比公平。

## 二、测试了什么内容，以及目的

M6 的测试不是"跑个分看看"，而是带着明确假设逐一验证。按时间顺序分为六个主题：

| 主题 | 测了什么 | 目的 |
|---|---|---|
| ① 检索通道消融 | 只用向量 / 只用 BM25 / 两者融合，三种跑法各测一轮 | 验证"双通道比单通道强"这个设计假设是否成立，各自强在哪类题上 |
| ② 查询扩展消融 | 依次叠加"查询改写"和"HyDE 假设性答案检索"两个增强技术 | 找出哪个技术真正有效、哪个是凑数的，避免无效复杂度 |
| ③ 生成层优化 | 改写生成答案的提示词（要求照抄原文细节、逐项答全、不许轻易说"不知道"） | 解决"文档找到了但答案说不知道"的问题 |
| ④ Agent 模式 | 让大模型多轮自主检索，对比单轮检索的 RAG 模式 | 验证"多轮检索能突破单次检索的文档数量上限"这个假设 |
| ⑤ 精排与引用治理 | 接入 rerank 精排模型；修复答案污染问题；裁剪最终引用的文档数量 | 提升送入大模型的文档纯度，减少干扰 |
| ⑥ 泛化性测试 | 把 64 道题改写成三种"用户真实问法"（口语化、关键词式、中文），重新测 | 回答"系统在真实用户不标准的问法下会掉多少分" |

前五个主题是**让分数变高**，第六个主题是**搞清楚分数在真实场景下还剩多少**——这是大多数同类项目不做、但我们认为必须做的事。

## 三、测试期间遇到的问题与解决

测试过程中发现的每个问题本身都是有价值的工程发现。按严重程度排序：

### 问题 1：BM25 索引每次启动都被清空（最严重，隐藏了一个多月）

**现象**：系统明明实现了关键词检索，但早期测试成绩和纯向量检索一模一样。
**排查**：检查发现判断"索引是否需要重建"的逻辑用错了判据——它检查数据库表的一个隐藏字段，而那种表（SQLite FTS5）的这个字段恒为 0，导致"需要重建"永远为真。**每次程序启动，索引就被删空重建，关键词检索从未真正工作过**，所谓"融合检索"一直 silently 退化成纯向量。
**解决**：改用表结构列集合做判据，并增加版本号登记表；另加了一个启动时健康检查，自动对比"文档总数"和"索引行数"，不一致就告警，防止再次静默失效。
**教训**：融合系统的某个通道失效时，整体功能看起来依然正常——**必须给每个通道单独做健康检查，不能只看最终结果**。

### 问题 2：43% 的文档正文在导入时丢失（影响最大的数据问题）

**现象**：修复问题 1 后成绩提升了，但某些题目涉及的关键词在整个语料库里搜不到任何结果。
**排查**：测试集不同栏目的文档，正文字段名不统一（有的叫 `content`，有的叫 `body`，字段名写在每份数据的清单里）。我们的转换脚本写死了只读 `content`，导致 **2248/5187 篇（43%）文档只剩标题没有正文**，64 道题里有 30 道的标准答案文档受损。
**解决**：转换脚本改为按数据清单声明的字段名拼接正文，全量重新导入。索引量从 7.3 万行恢复到 13 万行。
**教训**：**外部数据接入时，"字段名约定"必须由数据自己声明，不能靠猜**。这个 bug 如果靠"看总分"是发现不了的——总分只会偏低，不会报错。

### 问题 3：Agent 模式 41/64 题的答案是乱码标记（测试 r07 时暴露）

**现象**：Agent 模式测试时，64 题里 41 题的"答案"是一段 `<tool_call>` 原始标记文本，根本不是给人看的回答。
**排查**：Agent 循环在最后一轮会撤掉工具、要求模型直接作答，但模型看到历史消息里工具调用的格式，**用纯文本模仿了一遍工具调用格式**，程序以为"没有调用工具"就把这段文本当最终答案返回了。
**解决**：终答时检测是否含有工具调用标记——有则降级处理：把多轮检索积累的资料去重、精排、裁剪后，用 RAG 模式的成熟提示词重新合成一个干净答案。修复后泄漏 0/64。
**教训**：**大模型不会严格遵守"不要用文本模仿协议格式"的约定，程序必须做兜底检测**。

### 问题 4：rerank 精排在 RAG 模式下几乎无效（花了整整一轮测试买到的认知）

**现象**：接入精排模型后，RAG 模式的正确率不升反微降（35.94% → 34.38%）。
**排查**：逐题对比发现，"无效引用数"统计的是最终引用的 5 篇文档里有几篇不相干——而精排只是在 20 个候选内部重新排序，引用数量没变；并且测试集的陷阱文档和正确文档语义极度接近，精排模型同样分不出哪个是"正确的那个"、哪个是"冲突的那个"。
**解决**：保留精排（免费且对 Agent 模式有用），但修正它的价值定位：**它的战场是 Agent 模式下"从积累的一二十篇文档里剪出最相关的 5 篇"，不是 RAG 模式的重排**。
**教训**：一个技术在 A 场景无效不等于无用，**要看它作用在链路的哪个环节**。

### 问题 5：判分过程中网络中断会污染结果（流程性问题）

**现象**：一次判分跑到 57/64 题时本地断网，失败的题被裁判脚本**静默记 0 分**而不是跳过，结果文件看起来"完整"但已被污染。
**解决**：把受污染的结果作废重判，并在判分脚本里加强制校验：判分完成后自动统计网络错误次数，大于 0 就标记结果不可信。此后 13 轮判分全部零污染。
**教训**：**自动化评测链路里，"失败"和"低分"必须严格区分**，否则数据会说谎。

### 其他较小问题

- 多行命令换行符导致环境变量没传进程序（表现为启动 2.4 秒静默退出）→ 写成脚本统一收敛；
- 向量模型 60 秒超时对大模型偏紧 → 超时可配置，评测用 120 秒；
- 编辑配置文件时把配置块插错位置导致归属错位 → 编辑后必须检查缩进结构。

## 四、测试结果与数据分析

### 4.1 主成绩线：六步提升路径

| 阶段 | 配置 | 召回率 | 完整度 | 正确率 | 答对题数 |
|---|---|---|---|---|---|
| 起点 | 修复前（实际是残缺语料 + 纯向量） | 48.37% | 29.73% | 14.06% | 9/64 |
| 第一步 | 修复 BM25 索引 bug + 修复 43% 语料丢失 | 61.71% | 44.04% | 26.56% | 17/64 |
| 第二步 | + 查询改写 + HyDE | 66.20% | 50.53% | 35.94% | 23/64 |
| 第三步 | 换 Agent 多轮检索模式 | 75.22% | 47.91% | 40.62% | 26/64 |
| 第四步 | + 终答泄漏修复 + rerank 精排 | 77.38% | 51.83% | 39.06% | 25/64 |
| 第五步 | + 引用裁剪（最终引用精简到 5 篇） | **68.28%** | **53.29%** | **43.75%** | **28/64** |

注：第三、四行对应的是修复泄漏后的有效版本（r07b、r07c），原文中带 bug 的版本不计入。

三个值得注意的数据规律：

1. **提升最大的一步不是某个高级技术，而是修 bug**（第一步：召回率 +13.3pp）。两个隐藏 bug 修复的贡献超过后续所有新技术之和。
2. **Agent 多轮检索打破了数量上限**：单轮检索最多给大模型看 5 个文档片段，而要求"把散落信息拼全"的题目有的答案分散在 9 篇文档里——物理上不可能答全。Agent 模式让模型自己多搜几轮，引用量变成 2-20 篇，召回率从 66.20% 跳到 77.38%。
3. **引用越少，答案越对**（反直觉但数据明确）：把最终引用的文档从全部积累裁剪到 5 篇，召回率降了 9pp，但正确率反而升到 43.75%——因为上下文里的干扰文档少了，大模型不被带偏。**"给模型更多信息"和"给模型更干净的信息"是两回事，后者更重要。**

### 4.2 泛化性测试：分数在真实问法下还剩多少

把 64 道题用三种"真实用户可能的问法"改写后重测（最终配置）：

| 问法变体 | 召回率 | 正确率 | 召回率下降 |
|---|---|---|---|
| 原题（标准问法） | 68.28% | 43.75% | — |
| 口语化改写（去掉专业术语） | 40.23% | 26.56% | **-28.1pp** |
| 关键词式短查询 | 55.72% | 25.00% | -12.6pp |
| 中文提问（英文语料） | 21.88% | 14.06% | -46.4pp |

逐题型分析找到了掉分的具体原因：

- 含工单号、日期等**精确标记的题目最抗跌**（口语化下只掉 27pp），因为关键词检索能锚定这些标记；
- **需要语义理解的题目跌得最狠**（短查询下从 73.3% 掉到 33.3%），因为我们的查询增强技术依赖"一句完整的话"，用户只丢几个关键词时增强质量就塌了；
- **中文问英文库基本失效**，跨语言是独立的能力缺口。

这组数据的价值在于：**它如实标定了系统的适用边界**，并指出了下一步最有效的改进方向（在 Agent 规划阶段先做"把口语/关键词问法重写成专业检索词"的理解步骤）。

### 4.3 与开源框架的横向对比

EnterpriseRAG-Bench 官方排行榜上有 12 个系统跑过同一测试集（注意：官方是 500 题全集，我们是其中 64 题子集，数字口径不同，**只能比量级、不能比精确排名**）：

| 系统 | 类型 | 正确率 |
|---|---|---|
| Omni（自测口径） | Agent 多轮检索 + DeepSeek V4 Pro | 73.4 |
| OpenClaw | Agent 多轮检索 | 68.2 |
| 官方论文基线（BM25 + OpenSearch） | 传统检索 | 68.8 |
| OpenAI File Search | 大厂托管服务 | 61.0 |
| RAGFlow | 开源 RAG 框架 | 50.2 |
| Vertex AI Search | 大厂托管服务 | 41.9 |
| AnythingLLM | 开源 RAG 框架 | 35.6 |
| Open WebUI | 开源 RAG 框架 | 24.9 |
| **本系统（64 题子集口径）** | 自研 Agent + RAG | **43.75** |

对比可以得出三个结论：

1. **绝对水平**：我们的正确率放在官方榜单上，高于 AnythingLLM、Open WebUI 这类主流开源框架，低于用顶级商用模型（GPT-5 级、DeepSeek V4 Pro）的榜首系统。考虑到我们用的是中等档位的 GLM-5.3，这个差距里相当一部分是模型档位差距，不是架构差距。
2. **架构方向正确**：官方榜单前列的系统（OpenClaw、Omni）赢的方式都是"Agent 多轮检索 + 精排 + 干净合成"，与我们最终演化出的架构完全一致——这不是巧合，是殊途同归，说明这条路是对的。
3. **天花板认知**：整个榜单没有任何系统达到 70% 以上的正确率，"90% 准确率"在这类测试集上目前不存在。这个测试集的设计目标就是暴露问题，不是刷出漂亮数字。

## 五、结论

1. **成绩**：正确率从 14.06% 提升到 43.75%（3.1 倍），答对题数从 9/64 到 28/64，检索召回率最高达到 77.38%。放在同一测试集的开源框架中处于中上水平，架构形态与榜首系统一致。
2. **最大的贡献来自修 bug，不是堆技术**：两个隐藏 bug（索引每次启动被清空、43% 语料丢失）的修复贡献了最大涨幅。这印证了一个工程常识：**系统里静默失效的部分，比明面上的错误危险得多**——它们不报错，只让结果悄悄变差。
3. **每一分钱都花在了有数据支撑的地方**：11 轮消融测试让每个技术选型都有"开了多少分、关了多少分"的量化依据，包括两个"负结果"（查询改写单独无效、rerank 在 RAG 模式无效）——知道什么没用，和知道什么有用同样重要。
4. **泛化性是当前最真实的短板**：用户用口语问，召回率掉 28 个点。这不丢人——它明确了下一步的方向（查询理解前置），而且大多数同类项目根本不知道自己的系统有这个短板，因为没测过。
5. **遗留问题**（如实记录）：要求拼全多篇文档的题目答对率仍低（生成层整合能力不足）；细节复述类题目的正确率有波动；跨语言检索基本不具备。这三项已列入后续计划，对应的改进方案（Agent 读全文工具、查询理解前置、引用治理）已在评估中。
