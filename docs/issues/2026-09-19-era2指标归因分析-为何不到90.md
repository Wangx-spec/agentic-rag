# era-2 指标归因分析：为什么达不到 90%

> 2026-09-19。针对 r06（hybrid + rewriter + HyDE 全开，era-2 官方最优配置）的 64 题逐题拆解，
> 回答两个问题：**当前 66.20% recall / 35.94% correctness 的瓶颈在哪？90% 现实吗？**

## 一、结论先行

**90% 在 EnterpriseRAG-Bench 上不存在——不是"我们没做到"，而是目前没有任何系统做到。**

官方排行榜（500 题全集，12 个系统，按 correctness 排名）：

| 排名 | 系统 | Correctness |
|---|---|---|
| 1 | OpenClaw（agentic 检索循环） | 68.2 |
| 2 | OpenAI File Search | 61.0 |
| 3 | RAGFlow | 50.2 |
| 4 | Vertex AI Search | 41.9 |
| 5 | AnythingLLM | 35.6 |
| — | Omni（agentic 循环 + DeepSeek V4 Pro，自测） | 73.4 |
| 9 | Open WebUI | 24.9 |
| — | **本系统 era-2 r06** | **35.9（recall 66.2，已达一线水平）** |

官方论文基线：BM25+OpenSearch correctness 68.8% / recall@10 68.4%；纯向量（text-embedding-3-large）51.4% / 46.0%；
Bash agent 60.6% / 2.0 invalid extras。**我们的 recall 66.2% 与榜首（~68-69）只差 2-3pp，真正落后的是 correctness。**

benchmark 设计目标就是"难"：语料**故意注入内容冲突的近重复文档、故意放错位置的文档（8%）、垃圾干扰帖**；
判分规则为二元判且"答案中的具体数量必须与 gold 完全一致"。它是用来打脸"我的 RAG 很强"的，不是用来刷高分的。

## 二、r06 逐题拆解：三个瓶颈 + 一个模型档位问题

### 总分布

| 失败类别 | 题数 | 占比 | 定性 |
|---|---|---|---|
| 检索 100% 对但答错 | **16** | 25% | **生成层瓶颈** |
| 检索完全为 0 | **13** | 20% | **检索语义鸿沟**（12/13 单文档题） |
| 4+ gold 文档题（平均 recall 仅 30.6%） | 11 | 17% | **结构性上限** |
| 检索 100% 且答对 | 21 | 33% | —— |

recall 分布呈双峰：37 题 100%、13 题 0%、14 题 1-99%——要么找到要么全空，说明问题不在排序边缘抖动，而是硬命中/硬未命中。

### 瓶颈 A：`finalTopN=5` 是数学天花板（结构性）

r06 作答文件实测：**32/64 题恰好引用满 5 个文档**（topK=10 双通道召回 → RRF 融合后只取 finalTopN=5 个 chunk）。
completeness 题要求穷举（最极端一题 gold 为 9 个文档），5 chunk 上限意味着 recall 最高 5/9≈55%。
该题型 11 题只答对 1 题（9.09%），平均 recall 37.42%——**物理打不过，不是调优能解决的**。

### 瓶颈 B：低精度 + 冲突陷阱（benchmark 的核心考点）

每题平均混入 **3.09 个无效文档**进入生成上下文，而语料故意埋了数字冲突的干扰文档。典型：
- qst_0021（basic）：gold 说 "3 business days"，系统答 "48 hours"——被干扰文档的数字带偏；
- qst_0384（constrained）：completeness 100% 但优先级排序与 gold 不一致判错；
- qst_0327（intra-doc reasoning）：检索全对，但把 "token-generation-unit" 答成 "Token unit"——长文档远距离段落拼接出错。

**"抗干扰"正是这个 benchmark 考的核心能力，也是榜首系统靠 agentic 循环（读全文、交叉验证）赢的原因。**

### 瓶颈 C：语义鸿沟的硬骨头（检索侧剩余短板）

13 道零召回题题面全部是"拐弯问法"："外包人员默认访问权限多久过期""故障后头 60-90 分钟该做什么""新员工入职多久拿到全部权限"——
题面与文档零词汇重叠（BM25 失效），语义相似度也不高（向量失效）。HyDE 已救回一部分（r05 增益最大），剩余属于
embedding 模型对企业黑话/间接指代的覆盖盲区。

### 瓶颈 D：生成模型档位

榜首系统用 DeepSeek V4 Pro / GPT-5.x 级模型，本系统用 GLM-5.3（硅基流动）。
16 道"检索对但答错"中相当比例是数字精确复述、术语精确命中的失误——模型档位问题，不是 prompt 问题。

### 题型细分（r06）

| 题型 | 题数 | recall | correctness | 主瓶颈 |
|---|---|---|---|---|
| basic | 19 | 73.7 | 52.6 | 混合（干扰 + 生成） |
| semantic | 15 | 53.3 | 40.0 | 检索（瓶颈 C） |
| completeness | 11 | 37.4 | 9.1 | 结构（瓶颈 A） |
| constrained | 11 | 81.8 | 18.2 | 生成（瓶颈 B/D：数字与限定词） |
| intra-doc reasoning | 2 | 100.0 | 0.0 | 生成（长文档远距离拼接） |
| project_related | 2 | 62.5 | 0.0 | 多文档聚合 |
| conflicting / misc | 4 | — | 75-100 | —— |

## 三、改进路径（按预期收益/成本比排序）

1. **AGENT 模式评测（r07）**：榜首 OpenClaw 与 Omni 的共同赢法是 agentic 检索循环（search → 读全文 → 再搜 → 交叉验证 → 提交），
   本系统 `AgentLoop` + `SearchKnowledgeBaseTool` 已实现，需在 `EvalProperties` 加 `chat-mode` 开关。
2. **Reranker（bge-reranker 类）+ finalTopN 提至 8-10**：直接砍掉每题 ~3 个无效文档（瓶颈 B），并放松 A 的上限。
3. **completeness 题查询分解**：一题拆多路检索再合并，破 5-doc 结构上限。
4. **生成侧数字忠实度强化**：已有"照抄原文数字"指令，可加引用校验（答案中每个数字须标注来源 chunk）。

**现实预期：上述全做到，correctness 60-70% = 进入 SOTA 梯队；90% 不存在。**

## 五、r07 补充：AGENT 模式评测（2026-09-19 晚，重要发现）

r06 配置 + `EVAL_ERAG_CHAT_MODE=agent`（ReAct 工具循环，maxAgentRounds=5）跑完 64 题，判分零污染：

| 指标 | r06 (RAG) | r07 (AGENT) | 变化 |
|---|---|---|---|
| Document Recall | 66.20% | **75.22%** | **+9.0pp** |
| Completeness | 50.53% | 35.28% | -15.3pp |
| Correctness | 35.94% | 32.81% | -3.1pp |
| Invalid Extra | 3.09 | **10.27** | **×3.3** |
| 答对 | 23/64 | 21/64 | -2 |

### 5.1 检索侧：agent 循环显著有效 ✅

- 13 题 recall 上升；多文档题型大幅改善：completeness 37.4→53.6、constrained 81.8→**95.5**、project_related 62.5→87.5
- 每题引用文档数从恒 5（finalTopN 上限）变为 2-19——**瓶颈 A（5 文档结构天花板）被 agent 多轮检索自然打破**

### 5.2 生成侧：发现 AgentLoop 终答泄漏 bug ❌（r07 生成数字无效）

**41/64 题的"答案"是原始 `<tool_call>` 标记文本**（如 qst_0023 的答案就是一段 search_knowledge_base 调用标记）。

根因：`AgentLoop.run()` 在最后一轮撤掉 tools 让模型作答，但 GLM-5.3 看到历史消息里的工具调用格式后，
以**纯文本**形式模仿输出 `<tool_call>...</tool_call>`——`toolCalls()` 解析为空，被当作最终答案返回。
qst_0023 等 5 题 recall 100% 但 comp 掉到 0-8%，全是此 bug 所致，非模型能力问题。

**结论：r07 的 recall 75.22% / invalid extra 10.27 有效；correctness / completeness 被系统性压低，不能用于下结论。**

### 5.3 修复方案（r07b 待做）

1. 终答兜底：FINAL 分支检测到 `<tool_call>` 字样 → 不作为答案，改走 **RAG 合成**（用 `ctx.getSources()`
   累积的全部 chunk 走已调优的 RAG prompt 生成终答）——"agentic 检索 + RAG 合成"正是榜首系统的架构形态
2. 累积 sources 需先去重 + rerank 剪枝（r07 平均引用 10+ 文档、invalid extra 10.27，直接全喂会复现噪声问题）
3. 修复后重跑 r07b，预期：recall ~75 保持，correctness 冲 40+（超过 r06）

## 六、reranker 结论（详见《2026-09-19-M6加Reranker可行性评估》）

r07 把 reranker 优先级从"可选"推到"必做"：agent 模式 invalid extra 10.27（vs RAG 模式 3.09），
检索回来的文档更多但更脏，**没有精排就没有可用的 agent 检索**。硅基流动 bge-reranker-v2-m3 已实测可用
（免费、0.47s/20候选、gold 区分度 4.7 倍），工作量 0.5-1 天。

## 七、简历/面试口径

> "我的系统 RAG 模式 recall 66.2%，与官方榜首（~68）只差 2-3 个点；切到 AGENT 模式 recall 到 75.2%，
> 已超过榜首水平。评测还暴露了一个 agent 终答的协议泄漏 bug（模型在撤掉工具后以纯文本模仿 tool_call 格式，
> 41/64 题终答被污染）——这是只有认真做评测才能发现的工程问题。我的下一步是榜首系统的标准架构：
> agentic 检索 + reranker 精排 + RAG 合成终答。这个 benchmark 榜首 correctness 也只有 68%，
> 我清楚每个指标的位置和差距构成。"

这比一个虚高的分数更能打：**知道为什么低、低在哪、怎么补、补到哪算好**。
