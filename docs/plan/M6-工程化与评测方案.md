## 二、核心设计

### 评测框架

```
eval/
├── EvalRunner.java            — @Profile("eval") CommandLineRunner：加载评测集 → 逐题跑 → 汇总 → 写报告
├── EvalCase.java              — record(id, question, referenceAnswer, expectTool, mode)
├── AnswerAccuracyEval.java    — 回答 vs 参考答案：关键词重叠率（分词后 F1），阈值 0.5 记为准确
├── ToolSuccessEval.java       — Agent 模式下：是否调用了 expectTool + 参数非空 + 回答包含工具结果
└── datasets/eval-set.json     — 评测集（15~20 题：RAG 题 10 + 工具题 5 + 干扰题 3）
```

- 评测走内部服务调用（不启 HTTP 客户端绕圈），但路径与线上链路完全一致（同一 Controller 逻辑抽到 Service 层供两端复用——**这是 M6 的一个必要小重构**：ChatController 的链路逻辑抽到 ChatService）
- 报告输出：`eval-report.md`（总准确率、工具成功率、每题明细：命中/未命中关键词、工具调用记录、耗时）
- LLM 判分（可选开关 `eval.llm-judge: false`）：默认关——关键词重叠对 MVP 评测集足够，且可复现

## 六、关键取舍（面试可讲）

1. **关键词重叠 F1 而非 LLM 判分做默认**：可复现、零成本、无评判者波动；LLM 判分作为可选开关
2. **评测与线上同链路（下沉 Service）**：避免评测走旁路导致「评测分高、线上拉胯」
3. **K8s 只做最小集**：项目核心卖点是 Agentic RAG 链路，K8s 证明「会云原生部署」即可，不上 Operator/Helm 的复杂度
4. **不做 CI**：CI 是好故事但与项目卖点正交，独立成后续增强项
