## 二、核心设计

### 评测框架

```
eval/
├── EvalRunner.java            — @Profile("eval") CommandLineRunner：加载评测集 → 逐题跑 → 汇总 → 写报告
├── EvalCase.java              — record(id, question, referenceAnswer, sourceChunkIds, expectTool, expectedIntent, expectRefusal, mode)
├── AnswerAccuracyEval.java    — 回答 vs 参考答案：关键词重叠率（分词后 F1），阈值 0.5 记为准确
├── RecallEval.java            — 检索层：HybridRetriever 结果 vs sourceChunkIds，算 Recall@10
├── CitationEval.java          — 引用有效性：回答中的 [n] 引用是否真实存在于本次 sources（规则校验，量化幻觉）
├── ToolSuccessEval.java       — Agent 模式下：是否调用了 expectTool + 参数非空 + 回答包含工具结果
├── IntentRoutingEval.java     — 路由层：IntentClassifier 直跑（不走全链路），比对 expectedIntent
└── datasets/
    ├── eval-set.json          — 主评测集 20~25 题：RAG 题 12（标注 sourceChunkIds）+ 工具题 5 + 干扰/拒答题 4
    └── intent-set.json        — 意图路由集 20 条：四类意图 + MULTI_TASK 正反例（M5 验收的评测抽样从这出）
```

- 评测走内部服务调用（不启 HTTP 客户端绕圈），但路径与线上链路完全一致（同一 Controller 逻辑抽到 Service 层供两端复用——**这是 M6 的一个必要小重构**：ChatController 的链路逻辑抽到 ChatService）
- 报告输出：`eval-report.md`（总准确率、工具成功率、每题明细：命中/未命中关键词、工具调用记录、耗时）
- LLM 判分（可选开关 `eval.llm-judge: false`）：默认关——关键词重叠对 MVP 评测集足够，且可复现；企业实践中语义级判分（忠实度/回答相关性）用 LLM-as-judge（RAGAS/DeepEval 生态），个人项目保留可选开关即可，面试能讲清「为什么默认关」（可复现、零成本、无评判者波动）

### 评测分层（对标企业离线评测实践）

| 层 | 指标 | 实现 | 成本 |
|---|---|---|---|
| 检索层 | Recall@10 | sourceChunkIds 标注 + HybridRetriever 结果比对 | 标注即免费；顺手可跑「混合 vs 单向量 vs 单 BM25」消融 |
| 生成层 | 回答准确率（关键词 F1）+ 引用有效率（CitationEval） | 已有 + 规则校验 | 零成本 |
| Agent 层 | 工具调用成功率 | ToolSuccessEval（已有） | 零成本 |
| 路由层 | 意图路由准确率 | intent-set.json 直跑 IntentClassifier | 零成本（不走全链路） |
| 拒答/幻觉 | 无答案题正确拒答率 | 干扰题标 expectRefusal，回答含兜底话术记通过 | 零成本 |

> 在线评测（点赞点踩/追问率/trace 平台定位 bad case/Langfuse 类）企业必有，但个人项目无线上流量——不做，面试作为知识储备讲述即可。

### 语料与评测集建设（三源语料策略）

> 问题：独立开发，无企业文档。策略：三类语料各取所长，全部可合法进入开源仓库。

| 语料 | 来源 | 文档特征 | 用途 |
|---|---|---|---|
| **合成企业语料**（主力） | LLM 按模板生成虚构公司文档库：产品手册、API 文档、规章制度、FAQ、会议纪要，约 50 篇 | 完全可控、ground truth 可精确标注、演示时是真实企业场景 | 主体评测语料 + demo 演示素材 |
| 真实技术文档 | 开源项目官方文档节选（Apache 2.0/CC 许可，如 Spring Boot、PostgreSQL 中文文档） | 长文、标题层级、表格、代码块 | 考验 StructureChunker 与混合检索的难度档 |
| 公开数据集抽样 | DuReader / CMRC 2018 抽样 | 真实用户问句风格 | 只借「问题表述自然度」校准，不整库再分发（许可原因） |

**半自动 golden set 管线**（入库 → 出题 → 校验）：

```
LLM 按模板批量生成文档（带文档类型/长度/难度参数）
 → 入库，记录每篇文档的 chunkId 区间
 → LLM 基于具体 chunk 生成 QA 草稿（自动标注 sourceChunkIds + 参考答案）
 → 人工校验 20% 抽样（答案确实可由该 chunk 回答、无歧义）
 → 落入 datasets/eval-set.json（版本化，随仓库分发）
```

**两条红线**：① 个人工作区文档（agent-projects 下的评估/求职材料）严禁进入公开仓库——含隐私；② 语料许可必须允许再分发（Apache/CC BY/自产），不确定的只引用不复制的部分需逐条确认。

|---|---|---|---|
| **EnterpriseRAG-Bench**（onyx-dot-app） | ✅ 真实且工程成熟：50 万文档 + 500 题、HF 数据集 + parquet + 官方排行榜；模拟 AI 推理公司「Redwood Inference」，10 类问题分布明确（Basic 175 / Semantic 125 / 篇内推理 40 / 项目聚合 40 / 约束 30 / **矛盾文档 20** / 完整性 20 / 杂项 20 / 高层 10 / **信息缺失 20**） | ⭐⭐⭐⭐ **分类学与叙事契合度最高**：矛盾文档→幻觉压力测试；信息缺失→expectRefusal 拒答的外部版；Semantic（关键词重叠少）→FTS5 关键词通道与向量通道互补性的证明题；项目聚合/完整性→M5 多 Agent。约束：①50 万文档全量入库不现实（embedding 成本），且 Slack/Gmail/Linear 聊天工单格式与 StructureChunker（标题/段落导向）不匹配；②英文语料（embedding 模型须确认英文能力） | **抽切片**：只取 Confluence（5K 篇结构化文档，最贴合分块器）+ Conflicting/InfoNotFound/Semantic 三类题（约 165 题）；适配约 1-2 天。Onyx 排行榜允许开源项目提交（要求可复现）——README 报类别分数即可与社区对话，上榜则是硬背书。canary GUID 限制仅禁训练用途，评测不受影响 |

- **共性成本**：三个基准均为英文 + Python harness——embedding 模型需确认英文能力（bge-m3 / text-embedding-3 双语均可）；Python 脚本只读不改作参考，题目 jsonl 适配进 Java EvalRunner（与 CRUD-RAG 适配同套路）

### EnterpriseRAG-Bench 接入操作手册（2026-09-15 本地勘察定稿）

> 数据集已下载至 `agent-projects/EnterpriseRAG-Bench-main`（3.7GB / 51.2 万文件 / MIT 许可），以下是验证过的接入路径。

**一、数据集结构（勘察结论）**

```
EnterpriseRAG-Bench-main/
├── questions.jsonl                 # 500 题：question_id/question_type/source_types/question/
│                                   #   expected_doc_ids/gold_answer/answer_facts（含防幻觉反例约束）
├── generated_data/
│   ├── uuid_index.json             # dsid → 相对路径 映射（已验证 100% 可解析）
│   └── sources/{confluence,slack,gmail,linear,google_drive,hubspot,fireflies,github,jira}/
│                                   # 51.2 万个 JSON 文档（confluence 5,190 篇，均值 ~10KB）
├── answer_evaluation/              # 官方判分：answers.jsonl 进 → correctness/completeness/doc recall 出
├── src/scripts/answer_evaluation/  # metrics_based_eval.py（单系统打分）/ comparative_eval.py（双系统对比）
└── derived/                        # 本项目派生子集（已生成）
    ├── questions-confluence-64.jsonl   # source_types==['confluence'] 的 64 题（134 个 doc id 全部命中索引）
    └── questions-info-not-found-20.jsonl # 拒答题（source_types 为空，不依赖语料切片）
```

**二、关键勘察事实（决定接入方式）**

1. **题目按 source_types 完美切片**：500 题中 confluence-only 64 题（basic 19/semantic 15/constrained 11/completeness 11/misc 3/intra 2/project 2/conflicting 1），其 expected_doc_ids 经 uuid_index 验证 100% 落在 confluence 目录——**5,190 篇入库即可支撑 64 题全量评测，检索指标无泄漏风险**
2. **文档是 JSON 非纯文本**：confluence 文档含 title/space/author/labels/summary/content 字段，content 为纯文本（"Overview\n\nPurpose:" 式节标题，非 markdown #）——需写转换器：JSON → markdown（title 作 # 标题、content 的节标题行升级为 ##、labels 附加在头部），**文件名或文档名保留 dsid**（判分按 expected_doc_ids 对齐 document_ids，丢失 dsid = 无法算检索分）
3. **官方判分脚本的 LLM 只支持 OpenAI Responses API / Anthropic**（src/llm/factory.py 无 base_url）——用 DeepSeek 等国产模型做 judge 需小补丁（OpenAI() 加 base_url；若目标模型不支持 Responses API 需换 Chat Completions 调用），或直接用 OpenAI/Anthropic key 跑判分（64 题 × ~5 次 judge 调用，成本很低）
4. **answer_facts 含防幻觉反例**（"must not claim 180s is current"）——比本项目自有拒答题更强的幻觉约束，judge 逻辑直接受益

**三、接入步骤（对本系统）**

| 步 | 工作内容 | 验证 |
|---|---|---|
| S1 | 写转换脚本：confluence/*.json → agentic-rag/data/enterpriserag-md/*.md（# title + ## 节标题 + 正文 + 元信息头；文档名=dsid） | 抽查 3 篇 markdown 可读性 |
| S2 | 批量入库：调既有 ingest API（5,190 篇 × ~2.5K token ≈ 13M embedding token，云端 API 成本可控；异步任务状态机分批跑） | documents 表 5,190 行 DONE；Qdrant/FTS 计数对齐 |
| S3 | 出答案：EvalRunner 加载 derived/questions-confluence-64.jsonl，逐题走 RAG 模式（非 Agent 模式，先测基线），收集 answer + sources 的 dsid → 写 answers.jsonl `{question_id, answer, document_ids}` | 64 行 jsonl |
| S4 | 官方判分：`python -m src.scripts.answer_evaluation.metrics_based_eval --answers-file ... --no-correction`（先用 --no-correction 纯打分，跑通后再试三 judge 修正流） | results.json：correctness / completeness / doc recall / invalid extra docs |
| S5 | 报告落盘：四指标按题型分组写入 eval-report；对比基线（单通道 vs 混合）作消融 | README 引用「EnterpriseRAG-Bench Confluence 子集」分数 |

**四、边界与注意**

- **info_not_found 20 题**：不依赖语料切片可跑，但在 confluence-only 子库上「拒答」可能因干扰文档缺失而变容易（子库弱化了诱惑性干扰）——**作辅助指标单独报告，不并入主分**
- **全量 3.7GB 语料不进 git**：agentic-rag 仓库只放 S1 转换脚本 + derived 两个 jsonl（MIT 许可允许，但 5K 篇 markdown ~52MB 走 release 附件更干净）；README 注明数据来源与许可
- **英文语料**：embedding 模型需确认英文能力（bge-m3 / text-embedding-3 均可；当前云端模型需跑 S1-S3 前先用 10 题小样本验证英文检索质量）
- **conflicting_info 覆盖弱**（confluence-only 仅 1 题）：矛盾文档场景主战场在跨源题（14/20 含 confluence+其他源）——若后续要测矛盾场景，扩 jira 切片（+6,000 篇 → 覆盖 ~130 题）而非硬凑
- **溯源精度红利**：expected_doc_ids 是文档级标准答案，正好给 CitationEval 提供外部 ground truth——S3 收集 sources 时按 dsid 聚合 chunk，即得文档级引用评测

**开源门面红利**：「语料 + 评测集 + 报告可复现」随仓库分发，任何人 compose up + eval profile 即可复现准确率数字——这在开源 RAG 项目里是少数派配置。

## 六、关键取舍（面试可讲）

1. **关键词重叠 F1 而非 LLM 判分做默认**：可复现、零成本、无评判者波动；LLM 判分作为可选开关
2. **评测与线上同链路（下沉 Service）**：避免评测走旁路导致「评测分高、线上拉胯」
3. **K8s 只做最小集**：项目核心卖点是 Agentic RAG 链路，K8s 证明「会云原生部署」即可，不上 Operator/Helm 的复杂度
4. **不做 CI**：CI 是好故事但与项目卖点正交，独立成后续增强项
5. **合成语料为主 + 真实文档为辅**：合成企业语料的 ground truth 可精确标注、无隐私与许可风险、演示像真实场景；真实技术文档补检索难度档。「无企业文档」的限制转化为「半自动语料与 golden set 生成管线」的工程能力展示；在线评测（用户反馈/trace 平台）因无线上流量不做，作为知识储备
