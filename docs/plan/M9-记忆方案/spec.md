# M9 · 记忆持久化与调用策略 Spec

> 阶段：spec（已批准的决策见文末「决策记录」）
> 产出流程：spec.md → plan.md → task.md → checklist.md（逐份审批后才进入下一阶段）

## 背景

当前 agentic-rag 的记忆仅靠内存 / Redis 双实现（M4 的 `ConversationMemory`），Redis 实现 TTL 7 天，本质是「半持久缓存」：服务重启 / TTL 过期 / Redis 故障均会丢失会话历史；且没有跨会话的任何记忆能力——每个新会话都是白纸，用户需要重复交代偏好与背景。

对 ragent 的勘察结论：其记忆模块 = JDBC 会话消息持久化 + 最近 N 轮截断 + 滑动窗口摘要压缩（半窗口重叠防重复摘要、分布式锁防并发、小模型生成），**没有**实体记忆（用户画像）与长期记忆（跨会话语义检索）。

本方案采用三层记忆架构（对齐 mem0 / MemGPT 的业界范式，同时借鉴 ragent 的摘要压缩设计）：

| 层 | 内容 | 存储 | 生命周期 |
|---|---|---|---|
| 短期记忆 | 当前会话 messages 全量 | PG（持久化） | 会话存续 |
| 会话摘要 | 滑出窗口的历史压缩摘要 | PG | 会话存续 |
| 实体记忆 | 用户结构化偏好画像（语言、风格、既定决策等） | PG | 跨会话，按 userId |
| 长期记忆 | 有价值结论的摘要条目（带向量） | Qdrant + PG 元数据 | 跨会话，按 userId |

调用策略遵循「读 → 用 → 写」三阶段：

- **读**：新请求到达时，并行加载实体记忆 + 长期记忆语义检索（以用户消息为查询）+ 会话历史（含摘要），拼装进 prompt，Agent 带着完整用户画像进入任务
- **用**：任务执行中，短期记忆全程随行；Agent 可通过「记忆检索」工具临时发起长期记忆检索，结果注入当轮上下文，用完即走
- **写**：周期批量（每 N 轮）异步触发小模型「判断 + 提取」——偏好更新写入实体记忆，有价值结论向量化后写入长期记忆

## 目标

- 会话记忆真正持久化：服务重启、Redis 故障均不丢
- 长会话 token 可控：窗口截断 + 滑动摘要
- 用户画像跨会话积累，无需重复交代背景
- 有价值结论跨会话语义检索复用
- Agent 执行中可主动检索长期记忆（工具化）
- 数据模型与 M8 多用户方案兼容，届时零迁移

## 功能需求

- **F1 短期记忆持久化**：会话消息持久化到关系库（PG），提供与现有 `ConversationMemory` 等价的第三种实现（`jdbc`），加载时取最近 N 轮原文；`memory | redis | jdbc` 三态配置切换
- **F2 窗口控制与摘要压缩**：会话消息超过保留窗口（默认 8 轮）时截断；滑出窗口的部分由小模型异步生成增量摘要（与已有摘要合并去重、限制字数），摘要以系统消息形式拼在窗口历史之前；摘要与原文保持约半个窗口重叠，仅当重叠段完全滑出窗口才再次摘要（防每轮触发）
- **F3 实体记忆**：按 userId 存储结构化偏好画像（JSON 字段级更新，带时间戳）；任务开始时读取并注入 system prompt 开头；偏好冲突以最新为准
- **F4 长期记忆**：有价值的任务结论以摘要条目形式存储（向量 + 元数据：userId、时间、来源会话、原文摘要），独立向量集合（与知识库文档集合隔离）；任务开始时以用户消息为查询做语义检索，top-K 条注入 prompt
- **F5 记忆读取编排**：新请求到达时并行执行「实体记忆读取 / 长期记忆检索 / 会话历史（含摘要）加载」，合并拼装上下文；任一支路超时或失败则跳过该支路，不阻塞主链路
- **F6 记忆检索工具**：提供「检索长期记忆」工具注册进现有工具注册表（Agent 模式可用），以任意查询词检索当前用户的长期记忆，返回结果供当轮上下文使用
- **F7 周期批量写回**：每 N 轮（默认 5）对话后，异步触发一次小模型「判断 + 提取」：识别本批次的偏好表达与有价值的结论——偏好变更更新实体记忆（upsert），有价值结论向量化写入长期记忆；判定无新增则跳过写回；提取输出为结构化 JSON，解析失败跳过本轮不重试
- **F8 记忆管理接口**：提供按 userId 查看与清除实体记忆 / 长期记忆的管理 API（演示与调试用，无 UI）

## 非功能需求

- **N1 降级优先**：记忆的读与写任何一层失败（存储不可用、LLM 超时、JSON 解析失败）均静默降级，主问答链路不受影响；写失败仅记日志
- **N2 成本控制**：摘要生成与批量提取均使用可独立配置的小模型（配置项留空则回退主 LLM，模式与 M4 意图识别小模型一致）；每轮对话的额外 LLM 调用 ≤ 1 次（周期批量摊薄后远低于此）
- **N3 多用户兼容**：所有记忆数据按 userId 隔离；userId 为**数值型**（与 M8 `users` 表主键 `BIGINT` 同型），作为请求可选参数，缺省 `0`（系统/演示用户）；M8 接入用户体系后从登录态（UserContext）取真实 userId，缺省期间的存量记忆天然归属系统用户（与 M8 T3「存量数据归系统用户」的迁移策略一致），数据模型零迁移；长期记忆的向量 payload 使用与知识库文档一致的 ownerId 约定，M8 的检索 filter 机制可统一叠加
- **N4 记忆膨胀控制**：实体记忆单用户条目数有上限；长期记忆单用户保留最近 M 条（超限淘汰最旧）
- **N5 并发安全**：同一会话的摘要生成与批量提取不并发重复执行（单实例内用现有线程池 + 标记位即可，不引入分布式锁）

## 不做的事

- 不做记忆管理 UI（仅 API，F8）
- 不做 MemGPT 式 Agent 自主记忆编辑（写回走固定提取管线，Agent 不自行决定写什么）
- 不做跨用户记忆共享 / 群体记忆
- 不做 Redis 读缓存层（PG 直读；消息量级小，性能优化留后续）
- 不做会话标题生成、会话列表管理等周边功能（ragent 有，M9 不做）
- 不修改 M4 已交付的 `memory | redis` 两态行为（`jdbc` 为新增第三态）

## 验收标准

- **AC1**（F1）：使用 `jdbc` 模式进行多轮对话后重启服务，同一会话继续提问，回答能正确引用重启前的上下文
- **AC2**（F2）：单会话持续 30+ 轮后，发送给 LLM 的消息列表不超过窗口上限，且列表首条为摘要系统消息（日志或调试端点可观测）
- **AC3**（F3）：会话 A 中用户明确表达偏好（如「以后回答都用英文」），结束会话后新开会话 B，B 的首个请求拼装的 system prompt 中包含该偏好
- **AC4**（F4）：会话 A 中产生明确结论（如「项目截止日期是 10 月 15 日」），新开会话 B 提问「截止日期是什么时候」，长期记忆检索命中该条目并注入上下文
- **AC5**（F6）：Agent 模式下，LLM 自主调用记忆检索工具，成功取回跨会话的历史结论
- **AC6**（F7）：连续 10 轮对话，提取类 LLM 调用次数 ≤ 2 次（周期批量生效，日志可数）
- **AC7**（N1）：人为停掉向量库（或注入读超时），主问答链路仍正常返回（无记忆注入但不报错）
- **AC8**（F8）：管理 API 可列出某 userId 的实体记忆与长期记忆条目，清除后再次检索不再命中
- **AC9**（整体）：全部单元 / 集成测试通过，`./mvnw test` 绿

## 决策记录（需求澄清阶段产出）

| 决策点 | 结论 | 理由 |
|---|---|---|
| 记忆挂载主体 | 提前引入 userId（数值型，缺省 0 = 系统/演示用户），与 M8 users 表主键同型 | 实体/长期记忆的核心价值就是跨会话画像；数值型与 M8 对齐避免类型迁移，缺省 0 与 M8 T3 存量归系统用户的策略衔接 |
| 写回时机 | 周期批量（每 N 轮异步一次小模型判断+提取） | 成本可控；偏好表达本就留在当轮 messages，当前会话体验不受提取延迟影响 |
| 方案落位 | 独立 M9 方案，spec 四份文档流程 | M4 按原计划收尾不膨胀；M9 的短期记忆层扩展 M4 的 `ConversationMemory` 接口 |
| 摘要压缩 | 纳入方案（用户原设想未含） | 长会话下 messages 全量随行必然 token 失控；借鉴 ragent 半窗口重叠设计，自研实现 |
