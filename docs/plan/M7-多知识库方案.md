# M7 · 多知识库方案（库级隔离 + 检索过滤）

> 前置：M6 完成（评测/部署收口后做纯增量，不打断主线）
> 目标：多知识库创建与归属，入库/检索/Agent 工具全链路按库隔离，A 库的问题不命中 B 库的内容
> 验收：创建两个库各传一份文档，指定库提问只返回该库内容；不指定库时全库检索；隔离性评测用例通过

## 一、范围

**做**
- 知识库实体：`knowledge_bases` 表 + 建库/列表/删除 API
- 数据归属：documents / chunks 加 `kb_id`（ALTER 兼容，存量数据归入「默认库」）
- Qdrant payload 加 `kbId`（payload 是 schemaless 的，写入时直接带上，零结构变更）
- BM25：FTS5 表加 `kb_id` 列（含 bigram 化 content 不变），查询带库过滤
- 检索接口升级：`HybridRetriever.retrieve(query)` → `retrieve(query, kbIds)`；`VectorStore` 检索签名加过滤参数（kbIds 为空 = 全库）
- 入库 API：`POST /api/ingest` 加 `kbId` 参数（默认库兜底）
- Agent 工具：`search_knowledge_base` 加可选 `kbIds` 参数（M3 工具升级）
- 前端：库选择器（下拉：全部 / 具体库），请求携带 kbIds
- 评测：多库隔离用例（A 库问题在仅 A 库检索时命中、指定 B 库时不命中 A 内容）

**不做**
- 不做 LLM 自动选库（意图→库的路由属于「库路由意图」复杂度，显式选库够用，留后续增强）
- 不做每库一个 Qdrant collection（统一单 collection + payload filter）
- 不做库级配置差异（每库不同 topK/分块参数等）
- 不做跨库去重/合并策略（RRF 已天然处理）

## 二、核心设计

### 数据模型（增量迁移，全部向后兼容）

```sql
CREATE TABLE knowledge_bases (
    id          BIGSERIAL PRIMARY KEY,
    name        VARCHAR(128) NOT NULL,
    description VARCHAR(512),
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO knowledge_bases(id, name, description) VALUES (1, 'default', '默认库（存量数据）');

ALTER TABLE documents ADD COLUMN IF NOT EXISTS kb_id BIGINT NOT NULL DEFAULT 1
    REFERENCES knowledge_bases(id);
CREATE INDEX IF NOT EXISTS idx_documents_kb ON documents(kb_id);
```

- chunks 不加 kb_id（经 document_id 关联即可，避免冗余与不一致）
- Qdrant point payload 追加 `kbId`（入库时带上；**存量 point 无 kbId → 检索 filter 用 `must: kbId IN (...) OR kbId IS MISSING` 兼容，或重灌一次**——推荐重灌，评测集小）

### 检索过滤链

```
请求（kbIds 可选）
 → HybridRetriever.retrieve(query, kbIds)
     → QdrantStore.searchByVector(vector, topK, filter=kbId IN kbIds)   [payload filter，kbIds 空则不过滤]
     → Bm25Store.search(query, topK, kbIds)                              [WHERE kb_id IN (...)]
 → RRF 融合（不变）
```

- `VectorStore` 接口签名升级：`searchByVector(float[] vector, int topK, List<Long> kbIds)`（InMemoryVectorStore 同步适配，内存过滤）
- `RetrievedChunk` 透传 kbId + kbName（引用面板可显示库归属）

### 入库与 API

```
POST /api/kbs                     {name, description}        → 建库
GET  /api/kbs                     → 库列表（含文档数/块数统计）
DELETE /api/kbs/{id}              → 删库（级联删文档/chunks/Qdrant points/FTS 行）
POST /api/ingest?kbId=n           → 入库到指定库（缺省 1）
GET  /api/kbs/{id}/documents      → 库内文档列表
POST /api/chat {sessionId, message, mode, kbIds}              → 检索限定库范围
```

## 五、验收标准

- [ ] 创建两个库各传不同文档，指定 A 库提问只返回 A 库内容（引用面板可见库归属）

- [ ] 隔离性评测用例通过；全量测试绿

## 六、关键取舍（面试可讲）

1. **单 collection + payload filter 而非每库一 collection**：Qdrant 官方推荐模式；省去 collection 生命周期管理与多份 HNSW 索引的内存成本；中小规模过滤性能完全够用
2. **chunks 不冗余 kb_id**：经 document_id 关联推导，避免双写不一致；Qdrant payload 带 kbId 是检索性能需要（免回表），PG 侧无此需求
3. **显式选库而非 LLM 自动选库**：库数量少时显式选择零误判；「意图→库路由」是需要 prompt 调优的增强项，不与隔离基建捆绑交付
4. **存量兼容策略：重灌而非 filter 兜底**：评测集规模小，重灌一次干净彻底；`OR kbId IS MISSING` 的兼容 filter 是给大存量场景的方案，这里用不上（知道但不用，讲得出即可）
