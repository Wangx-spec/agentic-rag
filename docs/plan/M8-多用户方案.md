# M8 · 多用户方案（鉴权 + 归属隔离）

> 前置：M7 完成（多库是用户体系的存在前提：用户建自己的库）
> 目标：注册/登录（Sa-Token），库/文档/会话全部 owner 归属隔离，A 用户看不到 B 用户的任何资源
> 验收：两个用户各自建库传文档，互相不可见对方库/文档/会话；未登录访问受保护接口返回 401

## 一、范围

**做**
- 用户体系：`users` 表（用户名/密码 BCrypt 哈希）+ 注册/登录/登出 API
- 鉴权：Sa-Token（ragent 同款，熟悉度优先）+ 登录拦截器 + `/api/auth/**` 白名单
- 归属贯穿：knowledge_bases / documents 加 `owner_id`；Redis 会话记忆 key 加 userId 维度
- 隔离链：service 层统一「loadXxx 必带 owner」入口校验（防止 ID 遍历越权）；Qdrant payload 加 ownerId + 检索 filter 叠加；FTS 表加 owner 列
- 前端：登录页 + token 管理（localStorage + 请求头）+ 401 跳转
- 评测：越权用例（A 用户 token 访问 B 用户资源 → 404/403）

**不做**
- 不做角色权限（RBAC）——纯 owner 模型（资源属于创建者）
- 不做组织/团队/共享协作
- 不做注册开放治理（验证码/邀请码/邮箱激活）
- 不做管理后台（管理员查所有用户等）

## 二、核心设计

### 数据模型（增量迁移）

```sql
CREATE TABLE users (
    id           BIGSERIAL PRIMARY KEY,
    username     VARCHAR(64) NOT NULL UNIQUE,
    password     VARCHAR(128) NOT NULL,          -- BCrypt 哈希
    created_at   TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

ALTER TABLE knowledge_bases ADD COLUMN IF NOT EXISTS owner_id BIGINT REFERENCES users(id);
-- documents 经 kb 归属推导 owner，不冗余（与 M7 的 chunks 同理）
```

### 鉴权与上下文

```
POST /api/auth/register {username, password}   → 建用户（用户名查重 + BCrypt）
POST /api/auth/login    {username, password}   → 校验 → 签发 Sa-Token
POST /api/auth/logout                          → 登出

SaTokenInterceptor：除 /api/auth/**、/api/health、静态资源外全拦截
UserContext（ThreadLocal）：拦截器写入 userId，service 层读取
```

### 隔离链（防越权是核心，不是鉴权本身）

```
所有资源访问统一走 service 层入口：
  loadKb(kbId)     → WHERE id = ? AND owner_id = UserContext.getUserId()   找不到即 404
  listKbs()        → WHERE owner_id = ?
  ingest(kbId)     → 先 loadKb 校验归属再入库
  delete(kbId)     → 同上

检索 filter 叠加：Qdrant payload filter = (ownerId = ? AND kbId IN ...)
FTS：owner 列 + WHERE owner_id = ?
会话记忆：Redis key = chat:memory:{userId}:{sessionId}（跨用户 sessionId 碰撞天然隔离）
```

> 设计要点：**越权防护在 service 层做「归属校验」，而不是只在 Controller 校验参数**——ID 遍历（拿自己的 token 访问别人的 kbId）必须被拦。这是面试里「鉴权 ≠ 隔离」的话术核心。

### 前端

- 登录页（未登录自动跳转）；token 存 localStorage，请求头统一注入
- 401 响应统一拦截 → 清 token 跳登录页
- 现有功能（库/上传/四模式问答）全部在登录态下使用

## 四、任务拆解

| 任务 | 步骤 | 验证 |
|---|---|---|
| T1 用户与鉴权骨架 | users 表 + Sa-Token 依赖 + 注册/登录/登出 + 拦截器白名单 | curl：未登录 401；登录后携带 token 可访问 |
| T2 UserContext | ThreadLocal 上下文 + 拦截器写入 | 单测：上下文正确传递与清理 |
| T3 资源归属迁移 | kb.owner_id + 存量数据归系统用户 | 迁移后原功能回归 |

| T6 前端登录态 | 登录页 + token 注入 + 401 跳转 | 页面全流程：登录 → 建库 → 上传 → 问答 |
| T7 评测越权用例 | 越权访问用例 + 回归 | 越权用例全过；全量测试绿 |

## 五、验收标准

- [ ] 未登录访问任何受保护接口返回 401；`/api/auth/**` 与 `/api/health` 白名单可达
- [ ] A/B 两用户各自建库传文档：库列表、文档、检索、问答四方面互不可见
- [ ] A 用户用合法 token 直接请求 B 用户的 kbId/documentId → 404（防 ID 遍历）
- [ ] 同名 sessionId 在两个用户下记忆互不串扰
- [ ] 密码仅存 BCrypt 哈希（库内无明文）
- [ ] 登录后原有四模式问答、多库隔离功能全回归
- [ ] 全量测试绿

## 六、关键取舍（面试可讲）

1. **Sa-Token 而非 Spring Security**：功能面匹配（token 会话 + 拦截器）且轻；Spring Security 的 FilterChain/权限模型对本项目是过度配置
2. **owner 校验在 service 层而非 Controller**：鉴权（你是谁）与隔离（资源是谁的）分离；Controller 只管协议，越权防护在数据访问入口统一收口，杜绝旁路
3. **documents 不冗余 owner_id**：经 kb 推导，避免三处一致性问题；Qdrant payload 带 ownerId 是免回表的性能取舍
4. **纯 owner 模型不做 RBAC**：单租户个人场景 owner 够用；RBAC 是「有角色分化需求」才引入的，YAGNI
5. **BCrypt 而非 MD5/SHA**：慢哈希 + 自带盐，防彩虹表与 GPU 暴破的工程常识
