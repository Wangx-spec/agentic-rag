## 依赖关系与执行顺序

```
M1 ✅ → M2 ✅ → M3 ✅ ──┬─▶ M4 (体验+意图) ─▶ M5 (多 Agent) ─▶ M6 (评测+部署收口) ──┬─▶ M7 (多知识库) ─▶ M8 (多用户)
                         │                                                        └─▶ M10 (企业级增量，可选)
                         └─▶ M9 (记忆，M4 完成后即可开发；数据模型与 M8 对齐，双向兼容)
```

- M4/M5 依赖 M3 的模式分流；M6 收口依赖 M1-M5；M7/M8 是收口后的纯增量（多用户依赖多库存在，顺序不可逆）
- M4 与 M5 理论上可互换顺序（都只依赖 M3），但建议 M4 先——溯源 UI 让 M5 的多 Agent 演示效果更好

**为什么 M6 不后置到 M7-M10 之后（release train 而非 final boss）**：

1. **评测体系是增量的回归安全网**：M9 要改 ConversationMemory 签名、M10 要把内存消费者换成 MQ listener——先有 M6 的评测集，每个增量都能用「eval 跑分不降」验收；反过来则三个增量在无安全网下开发，评测首次跑出基线时问题无法归因
2. **可发布优先**：M6 = M1-M5 的 v1.0 收口，收口后随时处于「可投递」状态——deadline（10 月中旬）到了就投 v1.0，增量做多少算多少；把 M6 压到最后是 big-bang 集成，时间不够时面临「功能都在但没打包没评测」的最差交付态
3. **硬依赖**：M10 U4（S3 Multipart）依赖 M6 T9（MinIO）；`--profile mq` 双模式建立在 M6 完整 compose + healthcheck 之上
4. **工程化成本是增量的而非总量的**：M6 收 M1-M5 的口后，M7-M10 各自只追加一小块（compose profile、README 小节、评测集条目）——后置 M6 并不会让总工程量变小，只会让它挤在最后

## 每个方案的统一结构

范围（做/不做）→ 核心设计（类/接口/表结构/链路）→ 文件清单 → 任务拆解（T 序号 + 验证方式）→ 验收标准（可观测）→ 关键取舍（面试可讲）

## 全局约定

- 技术栈：Java 17 + Spring Boot 3.3 + 手写 OpenAI 兼容客户端 + Qdrant（VectorStore 接口可插拔）+ PostgreSQL（元数据）+ SQLite FTS5 + Redis
- 不依赖 LangChain / Spring AI / ES / 消息队列（MVP 方案已定的取舍，勿中途加回）
- 每个里程碑完成后 git commit 一次，message 前缀 `M{n}:`
- 每个里程碑的「验收标准」就是它的 DoD，逐项过完才算完成
