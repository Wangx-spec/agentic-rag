## 二、核心设计

### 1. 任务可靠投递（替换内存队列）

```
上传 → documents 落 PENDING → 发送普通消息（topic: ingest-task）
  → @RocketMQMessageListener 消费：
      幂等检查（仅 status=PENDING 才处理；PROCESSING/DONE 直接 ACK 跳过）
      → PROCESSING → 处理（复用 IngestService 逻辑）→ DONE / FAILED
  → 消费异常：RocketMQ 默认退避重试（16 次）→ 超限进死信队列 %DLQ%consumerGroup（日志告警）
```

**核心原则：「状态机做幂等、MQ 做投递」**——幂等不依赖 MQ 的任何语义（at-least-once 投递必然伴随重复），DB 状态机是唯一事实源；因此换回内存队列（默认模式）幂等依然成立。

### 2. 事务消息（文档删除的跨存储一致性）

**问题**：删除文档要清理 3 个异构存储（Qdrant 向量 + FTS5 索引 + 文件），本地 DB 事务无法覆盖；任一步失败留下脏数据，脏向量还会持续污染检索结果。

**方案（半消息模式）**：

```
DELETE /api/documents/{id}
  → 发送半消息（half message，消费方不可见）
  → 执行本地事务：documents.status = DELETING（DB 可回滚）
  → 执行清理：Qdrant delete(filter=documentId) + FTS5 delete + StorageClient.delete
      → 全部成功 → commit 消息 → 消费者置 DELETED（最终态）
      → 部分失败 → rollback 消息 → 消费者按 documents 表做补偿重试清理
  → broker 回查：超时未确认 → RocketMQLocalTransactionChecker 返回本地事务状态
```

**面试讲法**：这是「RocketMQ 事务消息保障删除任务可靠执行」的原型场景——本地事务管状态、半消息管触发、回查管兜底、补偿管最终一致。

### 3. S3 Multipart 分片上传（可选 U4）

```
前端 → POST /api/upload/init {fileName, fileSize}
        → 应用 CreateMultipartUpload → 返回 uploadId + 每片预签名 URL
前端 → 并发 UploadPart 直传 MinIO        ← 文件流量旁路应用服务器
断点 → GET ListParts → 前端跳过已传分片   ← 续传 = 协议原生
完成 → POST /api/upload/complete → CompleteMultipartUpload（服务端合并）
超时 → 定时任务 AbortMultipartUpload 清理未完成的脏分片
```

分片元数据由存储层管理（应用零分片表）；对比自管分片方案（DB+Redis 双写一致性补丁）的优劣分析见 plan/README 决策记录。

### 4. MCP server 暴露（可选 U6，2026-09-08 增补）

```
agentic-rag 应用
  ├── [进程内] AgentLoop → ToolRegistry → SearchKnowledgeBaseTool（直调，低延迟，M3 原样）
  └── [对外]  McpServerEndpoint（官方 Java SDK io.modelcontextprotocol:mcp，Streamable HTTP）
              暴露: search_knowledge_base / list_documents / calculator
              复用: 同一批 Tool 实现（双面工具——对内直调、对外 MCP，单一实现）
                ↑
        其他 MCP client：Claude Code / IDE / 团队其他 Agent 应用（含本项目 MedAgents、WaLiAPI 网关）
```

**关键设计**：
- 双面工具：`Tool` 接口的同一实现，进程内由 AgentLoop 直调；MCP endpoint 仅做协议包装（tools/list、tools/call 的 JSON-RPC 映射）——零重复实现
- M3 的接口四件套（name/description/inputSchema/execute）本就与 MCP 定义一一对齐，包装成本极低
- 与 **playground（agent-infra-playground）的 rag-service 模块同体**：playground 里「RAG 底座服务」的实现形态就是这个 MCP server——一次工作、两个产出

**验证**：Claude Code 或任意 MCP client 连接后 `tools/list` 可见、`tools/call` 调用检索返回结果。

## 六、关键取舍（面试可讲）

1. **「状态机做幂等、MQ 做投递」职责分离**：幂等不依赖 MQ 语义（at-least-once 必然重复投递），DB 状态机是唯一事实源——换回内存队列幂等依然成立，这是双模式开关可行的原因
2. **事务消息解决异构存储删除一致性**：本地 DB + 向量库 + 文件存储无法用单一本地事务覆盖；本地事务管状态、半消息管触发、回查管兜底、补偿管最终一致
3. **双模式开关（memory 默认 / mq profile）**：轻量定位不变，扩展路径可演示——「什么时候需要 MQ」的判断本身就是答案
4. **S3 Multipart 而非自管分片表**：分片元数据归属存储层、应用无状态、流量旁路（对比自管方案需 DB+Redis 双写一致性补丁）
5. **RocketMQ 而非 Kafka**：Java 生态原生 starter、事务消息能力（Kafka 无对应）、5.x Proxy 模式单容器部署轻于 KRaft
