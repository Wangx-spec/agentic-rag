# 查询理解前置 — plan（技术设计）

> 对应 spec：`2026-09-22-查询理解前置-spec.md`
> 日期：2026-09-22 | 状态：已批准

## 1. 架构概览

新增一个**查询理解服务**，挂在 AGENT 链路入口（`ChatService.runAgent` 构建 AgentContext 之前）。一次 LLM 调用产出 `{intent, normalized_query, sub_queries}`；成功后把「检索引导」作为一条额外 system 消息注入 Agent 消息列表，并把意图填入 ChatResult。失败则静默跳过。AgentLoop、检索层、工具层全部零改动。

```
用户问题
   │
   ▼
ChatService.runAgent
   │ ① 查询理解（开关开启时，一次 LLM 调用，fail-open）
   │    产出：intent + normalized_query (+ sub_queries)
   │ ② 注入「检索引导」system 消息 + 意图填入 ChatResult.routedIntent
   ▼
AgentContext（原始问题原样保留）
   ▼
AgentLoop ReAct 循环（零改动）
```

**对 spec F2/N2 的修正说明**：读码确认 AGENT 链路（runAgent）目前**不调用** IntentClassifier（分类只发生在 AUTO 路由）。因此查询理解在 AGENT 模式是**净增 1 次 LLM 调用**（不是净增为零）；AUTO 模式下若后续复用此服务才是净增为零。顺带的收益：查询理解产出的意图可填入 ChatResult.routedIntent（AGENT 模式该字段目前恒为 null）。

## 2. 核心数据结构

### 2.1 QueryUnderstanding（record，`intent` 包）

| 字段 | 类型 | 说明 |
|---|---|---|
| intent | Intent（现有五类枚举） | 分类结果，与 IntentClassifier 口径一致 |
| confidence | double | 置信度（沿用现有口径，低于阈值视为无效） |
| normalizedQuery | String | 规范查询；非 KB_QA / MULTI_TASK 可为空 |
| subQueries | List\<String\> | 仅 MULTI_TASK 时非空，每个独立子问题一条 |

### 2.2 QueryUnderstandingService（新组件）

| 方法 | 说明 |
|---|---|
| `Optional<QueryUnderstanding> understand(String userMessage)` | 开关关闭 / LLM 调用失败 / 解析失败 / 低置信 → `Optional.empty()`；成功返回结构化结果 |

### 2.3 配置（RagProperties.Agent 增 1 字段）

- `queryUnderstandingEnabled`（默认 `true`）
- yaml：`rag.agent.query-understanding-enabled: ${RAG_AGENT_QUERY_UNDERSTANDING_ENABLED:true}`
- 与 citationTopN、document-tools-enabled 同一风格，评测环境变量可覆盖。

## 3. 模块设计

### 3.1 QueryUnderstandingService（新建 `intent/QueryUnderstandingService.java`）

**职责：** 一次 LLM 调用完成「意图分类 + 规范查询生成 + MULTI_TASK 子查询拆解」，解析容错，全程 fail-open。

**提示词要点：**
- 五类意图（CHAT / KB_QA / MULTI_TASK / TOOL_TASK / OFF_TOPIC）的定义与示例与现有 IntentClassifier **保持一致**（口径统一，结果可对比）。
- `normalized_query`：保留原意、补全术语/展开缩写、检索友好；长度不超过原问题 1.5 倍；它不是改写用户问题本身，而是给 Agent 的「检索建议」。
- `sub_queries`：仅 intent = MULTI_TASK 时输出，每条是一个可独立检索的子问题。
- 输出约束：只返回 JSON，不要多余文字。

**解析逻辑：**
1. 复用 IntentClassifier 的容错思路：去除 ```` ```json ```` 包裹、trim。
2. JSON 非法、intent 不在五类枚举、confidence 低于 `IntentProperties.confidenceThreshold` → 返回 `Optional.empty()`。
3. normalizedQuery 为空串 → 归一化为 null；subQueries 缺失 → 空列表。

**依赖：** LlmClient、IntentProperties（复用置信度阈值，避免新增配置）、RagProperties（开关）。

### 3.2 ChatService.runAgent（修改，约 15 行）

**改动点：**
1. 构建 AgentContext 前调用 `queryUnderstandingService.understand(userMessage)`。
2. 存在结果时：在 `buildAgentMessages` 的主 system 消息之后**追加**一条「检索引导」system 消息，内容形如：

   > 检索引导：建议优先使用以下检索查询调用 search_knowledge_base："<normalizedQuery>"。
   > （MULTI_TASK 时追加：该问题包含多个子问题，建议逐一检索：<subQueries 列表>。）
   > 最终回答必须对齐用户原始问题。

3. ChatResult 的 routedIntent 由 `null` 改为理解结果的意图；查询理解缺失（empty）时保持 `null`，行为与现状一致。

**不改动**：buildAgentMessages 的原有结构、AgentContext 构造参数、AgentLoop 全部逻辑。

## 4. 模块交互

- **运行**：`runAgent` → `understand()` →（成功）注入引导消息 + 打日志（可见意图与规范查询，便于归因）→ AgentLoop 正常跑。
- **评测**：EnterpriseRagRunner 走 `chat(..., AGENT, ...)` 入口，自动经过新逻辑，评测代码零改动；开关经环境变量控制，r09 单变量成立（r07d 口径其余配置全同）。
- **与 QueryRewriter 的关系**：规划期前置（改 Agent 的查询组织）与检索层改写（改单路检索）叠加不冲突，r07d 口径里改写保持开启。

## 6. 技术决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 注入位置 | system 消息（主提示之后追加） | 不污染用户消息流；原始问题原样保留，作答对齐与判分口径不变 |
| 结果缺失语义 | Optional.empty = 跳过 | 与 fail-open 一致，调用方无分支负担 |
| 意图枚举 | 复用现有 Intent 五类 | 口径统一，与 AUTO 路由结果可对比；不新增类型（YAGNI） |
| 置信度阈值 | 复用 IntentProperties.confidenceThreshold | 避免新增配置；低置信 = 不理解，跳过 |
| 开关位置 | `rag.agent.*` 同级 | 与 citationTopN、document-tools-enabled 同一风格 |
| 评测轮次 | r09 原题 + r09v1 变体两轮 | 原题防回退、v1 验证目标；沿用单次运行判定纪律 |
| 注入文案语言 | 中文引导 + 原样引用规范查询 | 与现有系统提示风格一致 |

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 引导消息反而限制 Agent 灵活性 | 原题 corr 回退 | 文案用「建议优先」而非「必须」；AC5 设 ±3pp 回退红线，触发则默认关闭开关 |
| LLM 输出 JSON 不稳定 | 功能失效 | 解析容错 + fail-open；单测覆盖非法 JSON 路径 |
| 净增 1 次 LLM 调用拖慢评测 | r09 耗时略增 | 单次调用 < 2s，64 题预算内可忽略；评测机硅基流动免费档可承受 |
