# M6 性能优化方案 - BM25 修复与泛化性建设

## 一、RAG 性能测试中遇到的问题（简要）

### 1.1 评测环境问题
- **Jackson 映射失败**：jsonl 用 snake_case，Java record 用 camelCase，导致 question_id / expected_doc_ids 全为 null，需加 `@JsonProperty` 注解。
- **IDE 后台编译污染**：IDEA 的 ECJ 编译器未生成 record 访问器，污染 target/classes，需关 IDE 或只删 target/classes（不能 mvn clean，会删 94MB 的 bm25.db）。
- **Phase 4 判分全 0 假结果**：LLM_PROVIDER 等环境变量缺失 + 官方脚本 `except: continue` 静默重试吞错，表现为全 False 但 recall 正常，需加 preflight 预检。

### 1.2 BM25 通道重大缺陷（**核心问题**）
- **索引恒空导致通道失效**：`Bm25Store.needsRebuild()` 用 `PRAGMA table_xinfo` 判断 `content` 列 `hidden==0` 来触发重建，但 FTS5 中所有显式声明列（含 UNINDEXED）的 hidden 恒为 0，只有虚拟列才为 1，导致每次 JVM 启动都 `DROP TABLE` 重建空表。实测 bm25.db 94MB 但 FTS 行数为 0、99.97% 是空闲页，评测分两次会话（导入/作答），第二次启动即清空索引。
- **RRF 静默退化**：`HybridRetriever` 对 BM25 空结果无日志/断言，RRF 融合时静默退化为纯向量单通道。**当前四指标（recall 48.37% / completeness 29.73% / correctness 14.06%）是纯向量成绩，不含 BM25 贡献**，需重新解读为"单通道基线"。
- **测试覆盖盲区**：`Bm25StoreTest` 用 `@TempDir` 只在同一目录构造一次 store，"二次构造清空索引"这条路径零覆盖。

### 1.3 查询构造与数据集不匹配
- **全 AND 匹配废掉长查询**：`toMatchQuery()` 给每个 token 套双引号，FTS5 隐式 AND。实测 benchmark 64 题中位数 32 个 token（最小 12、最大 65），且 "How"/"is"/"the" 等停用词也参与 AND，单个 chunk 不可能同时包含 32 词，**即使修好索引，BM25 在当前长问句 benchmark 上也几乎不会命中**。
- **反转悖论**：当前实现在术语密集长问句（= benchmark）上被全 AND 打死表现差，但在短关键词查询（= 很多真实场景）上反而好，泛化性问题是双向的。
- **缺少归一化与停用词过滤**：无英文词形归一（"running" vs "run"）、无停用词表、bigram 无 idf 选择、ID/编号这类低频高区分度 token 未单独加权。

### 1.4 检索与生成层短板
- **检索短板（semantic 召回 26.7%）**：qst_0183 recall=0 幻觉答错，query 改写/多查询扩展不足。
- **生成过度保守（constrained correctness 0/11）**：qst_0382 recall=100% 却回答"无法回答"，qst_0013 部分拒答，RAG prompt 未鼓励尽力作答+覆盖问题所有子项。
- **约束型细节遗漏**：qst_0381 recall 高但漏 ticket 号/日期，生成完整性不足。

### 1.5 评测体系缺陷
- **单一评测集无法暴露泛化衰减**：benchmark 题面术语密集且语料术语一致，恰好压在 BM25 甜区（如果它能跑的话），缺 query 变体与通道消融。
- **缺泛化性量化指标**：没有"换个人换个问法，检索还稳不稳"的度量。

## 二、优化方案（按优先级与依赖关系排序）

### Phase 1：BM25 通道修复与验证（1 天，**前置依赖**）

**目标**：让 BM25 真正跑起来，建立通道级可观测性。

#### 1.1 修复 `needsRebuild()` 索引判据（核心）
- **问题**：当前用 `table_xinfo` 的 `hidden` 字段判断，但该字段对所有显式声明列恒为 0。
- **方案**：改用 `PRAGMA table_info(chunks_fts)`（只返回 6 个声明列，实测不含虚拟列），检查是否同时存在 `document_id` / `indexed_content` 且 `content` **不在**返回列表中（因为它被声明为 UNINDEXED）。
- **补充安全**：
  - 加一张 `bm25_meta(schema_version INT)` 表，按版本号重建（当前 v1）。
  - DROP TABLE 时输出 WARN 日志：`"BM25 索引 schema 变更，重建中..."`。
- **回归测试**：`Bm25StoreRebuildTest`，覆盖"同一 dataDir 构造两次 store，第二次不应清空第一次的数据"。

#### 1.2 加通道健康断言
- **启动时断言**：`Bm25Store` 构造后，执行 `SELECT count(*) FROM chunks_fts`，若为 0 且 `document_id` 表有数据，WARN：`"BM25 索引为空但元数据存在，索引可能未正确初始化"`。
- **检索时断言**：`HybridRetriever.retrieve()` 中，若 `bm25Results.isEmpty()` 且 `vectorResults.size() > 0`，WARN：`"BM25 通道空结果，hybrid 退化为纯向量"`，并输出 query 前 50 字。
- **评测报告增强**：Phase 4 输出 BM25 非空率（`bm25_hit_count / total_queries`）和唯一命中率（`unique_to_bm25 / total_queries`），度量通道独立贡献。

#### 1.3 消融基线重跑（验证预测）
- **三路对比**：只 BM25 / 只向量 / RRF，各跑 64 题，确认修复后 BM25 的实际贡献。
- **可证伪预测**：若 BM25 单路 recall < 10%，说明全 AND 长查询假设成立；若 > 30%，说明 AND 语义判断有偏差，需调整优化方向。
- **产出**：`docs/issues/2026-09-16-BM25修复后通道消融对比.md`。

### Phase 2：查询构造优化（1.5 天，**可与 Phase 3 并行**）

**目标**：解决全 AND 废掉长查询 + 补齐归一化短板，提升 BM25 在多样查询形态下的命中率。

#### 2.1 AND 失败降级 OR
- **策略**：先执行全 AND 匹配（`"token1" "token2" ...`），若返回 < 3 条，自动降级为 OR（`token1 OR token2 OR ...`），取 top-K。
- **日志**：降级时 DEBUG：`"BM25 AND 查询返回 X 条 < 3，降级 OR"`。

#### 2.2 停用词过滤 + 英文词形归一
- **停用词表**：`resources/stopwords-en.txt`（"the", "is", "and", "or", "a", "an", "in", "on", "at", "to", "for" 等 50 词），在 `toMatchQuery()` 前过滤。
- **词形归一**：英文 token 用 Porter Stemmer（轻量，无外部依赖）归一为词根，写入 `indexed_content` 时同步归一。
- **中文保持 bigram**：保留现有逻辑，但可考虑加 idf 筛选（只保留 idf > 某阈值的 bigram，减少噪声）。

#### 2.3 ID/编号/日期单独加权
- **识别规则**：正则 `\b[A-Z]+-\d+\b`（如 JIRA ticket "CONF-1234"）、`\b\d{4}-\d{2}-\d{2}\b`（日期）、`\b[A-Z0-9]{6,}\b`（长编号）。
- **加权策略**：这类 token 在 FTS5 查询中用 `^2.0`（boost 2 倍），或单独 OR 子句：`(normal_tokens) OR (id_tokens)^2.0`。
- **目标**：解决 qst_0381（recall 高但漏 ticket 号）类失败。

### Phase 3：检索层增强 - Query 改写与多查询扩展（1.5 天，**可与 Phase 2 并行**）

**目标**：主攻 semantic 召回 26.7%，通过查询变体增加召回覆盖。

#### 3.1 Query 改写（Rewriter）
- **方案**：用 LLM 生成 1-2 个改写查询（同义改述、扩展术语、补充背景），与原查询并行检索，结果合并去重。
- **Prompt 模板**：
  ```
  你是检索优化专家。用户问题："{query}"
  请生成 1 个改写版本，要求：
  1. 保留核心意图，用同义词/相关术语替换
  2. 适当扩展背景信息（如缩写展开）
  3. 保持简洁，不超过原问题 1.5 倍长度
  只返回改写后的问题，无需解释。
  ```
- **实现**：`QueryRewriter.rewrite(String query) -> List<String>`，返回 `[原查询, 改写1]`。
- **成本控制**：只对 token 数 > 15 的查询做改写（短查询无需），用 cheap_llm（如 GLM-4-Flash）。

#### 3.2 多查询扩展（HyDE 轻量版）
- **方案**：对原查询生成 1 个"假设性答案片段"（50 词），用该片段做向量检索，与原查询检索结果 RRF 融合。
- **Prompt 模板**：
  ```
  假设你是企业知识库。用户问题："{query}"
  请生成一个简短的答案片段（50 词内），包含可能出现在文档中的术语和细节。
  只返回答案片段，无需解释。
  ```
- **适用范围**：只对 semantic / basic 题型（非 constrained）启用，避免 HyDE 引入不存在的细节。

#### 3.3 评估增强
- **消融对比**：原始 / +改写 / +HyDE / +改写+HyDE，各跑 64 题，记录 semantic 召回变化。
- **成本记录**：统计 LLM 调用次数与 token 消耗，评估生产可行性。

### Phase 4：生成层优化 - RAG Prompt 改进（0.5 天）

**目标**：解决过度保守（constrained correctness 0/11）与细节遗漏。

#### 4.1 Prompt 改进点
- **去保守**：当前 prompt 若含"无法确定则回答'无法回答'"，改为"若信息不完整，基于现有上下文尽力作答，并标注不确定部分"。
- **要求覆盖所有子项**：约束型问题若有多个子问（如"列出所有 X，包括 Y 和 Z"），明确要求"逐项回答，不可遗漏"。
- **引导引用原文**：要求生成答案时引用具体 chunk 编号或原文片段，提升可追溯性。

#### 4.2 验证
- 手工验证 qst_0382（recall=100% 却拒答）、qst_0013（部分拒答）、qst_0381（漏细节）三题，确认改进后 correctness 提升。

### Phase 5：泛化性评估体系建设（1 天）

**目标**：建立"换个人换个问法，检索还稳不稳"的量化指标，防止指标被单一 benchmark 带偏。

#### 5.1 Query 扰动集构建
从 64 题派生 3 类变体（gold doc 不变）：
1. **去术语化（口语改写）**：用 LLM 将问题改为日常口语，避免专业术语。例：  
   `"What is the validity period for the telemetry driven runbook author certification?"`  
   → `"How long does the certification for writing telemetry runbooks last?"`
2. **短查询（关键词抽取）**：抽取 5-8 个核心关键词，去掉疑问词和连接词。例：  
   → `"validity period telemetry runbook certification"`
3. **跨语言（中译）**：将问题翻译为中文，gold doc 仍为英文（测试跨语言鲁棒性，但这要求 embedding 模型支持多语言）。

**生成脚本**：`scripts/generate_query_variants.py`，调用 LLM 批量生成，输出 `derived/questions-variants-*.jsonl`。

#### 5.2 泛化性指标
- **Recall 掉幅（Recall Drop）**：`(原始 recall - 变体 recall) / 原始 recall`，越小越鲁棒。
- **通道独立贡献率**：只有 BM25 召回 gold doc 的题占比，度量 BM25 不可替代性。
- **验收门槛**：
  - 去术语化 recall drop < 15%
  - 短查询 recall drop < 10%（BM25 甜区）
  - 通道独立贡献率 > 10%（说明 BM25 确实补了向量的盲区）

#### 5.3 评测报告模板
`docs/issues/2026-09-XX-泛化性评估报告.md`：
- 基准 recall（原始 64 题）
- 三类变体 recall 与掉幅
- 通道消融对比（只 BM25 / 只向量 / RRF）
- 典型失败 case 分析（每类变体各 2 例）

### Phase 7：Rerank 精排与 Agent 终答修复（2026-09-19，代码改造已完成）

**背景**：r06（RAG 全开）invalid extra 3.09、r07（AGENT 模式）invalid extra 10.27 且 41/64 题终答泄漏 `<tool_call` 标记，correctness 32.81% 因泄漏作废。榜首系统普遍采用「agentic 检索 + reranker 精排 + RAG 合成终答」架构，本 Phase 对齐该形态。

#### 7.1 RerankClient（硅基流动 /v1/rerank）
- **模型**：`BAAI/bge-reranker-v2-m3`（硅基流动免费、Cohere 兼容协议）。
- **接口**：`Optional<List<RerankResult>> rerank(query, documents, topN, model)`，复用 `LlmProperties`（baseUrl/apiKey/timeoutSeconds）。
- **工程细节**：
  - DCL 懒加载 `HttpClient`（与 `EmbeddingClient` 同模式，connectTimeout 15s）。
  - 网络异常重试 1 次（间隔 1s），4xx/5xx 不重试。
  - **fail-open**：任何失败路径返回 `Optional.empty()`，调用方检测 empty 后回退 RRF 序。
  - `@Autowired(required=false)`：RerankClient 可选注入，关闭时系统行为与改动前完全一致（向后兼容）。
- **测试**：`RerankClientTest` 5 项（成功 / 4xx / 超时 / 空文档 / 未配置），用 JDK 内置 `com.sun.net.httpserver.HttpServer` mock 硅基流动 API。

#### 7.2 HybridRetriever 接入 rerank 分支
- **插入位置**：RRF 融合后、构造 `RetrievedChunk` 列表前。
- **流程**：`merged.values()` → 按 rrfScore 降序取 `candidateSize`(20) → rerank → 取 `finalTopN`(5)。
- **配置回退**：`rerank.finalTopN` 为 null 时回退 `retrieval.finalTopN`。
- **fail-open**：rerank 失败时回退 RRF 序截断，记 WARN 日志 "Rerank 调用失败，回退 RRF 序"。
- **测试**：`HybridRetrieverTest` 3 项（rerank 关闭 / 开启成功 / 失败回退）。

#### 7.3 AgentLoop 终答泄漏检测 + RAG 合成降级
- **检测点**：两个终答分支（正常终答 + 超轮次终答）的 `response.content()` / `finalContent`。
- **触发条件**：终答包含 `<tool_call` 字符串字面量。
- **降级流程**：
  1. 取 `ctx.getSources()`（executeTool 中累积，比 spec 原案的消息解析更可靠）。
  2. `deduplicateByDocumentId`：按 documentId 去重。
  3. `rerankPruneIfEnabled`：可选 rerank 剪枝取 top 8。
  4. `synthesizeRagAnswer`：构造 RAG system prompt（复用 ChatService 4 条准则）+ 调 `llmClient.chat()`。
- **边界**：sources 为空时返回原始终答（无法降级）；RAG 合成异常时返回兜底文案。
- **测试**：`AgentLoopTest` 9 项（原 6 项 + 新增 3 项泄漏检测：无泄漏 / 泄漏+sources / 泄漏+无 sources）。
- **工程坑**：测试文件中 `<tool_call` 字面量被系统误解析为工具调用标记导致文件截断，用 `"<" + "tool_call"` 字符串拼接规避。

#### 7.4 配置与脚本
- `application.yaml` 新增 `rag.retrieval.rerank` 段（enabled/model/candidateSize/finalTopN）。
- `scripts/run-erag-round.sh` 新增第 5 参数 `RERANK`，透传 `RAG_RETRIEVAL_RERANK_ENABLED`。

## 四、面试叙事素材（核心亮点）

1. **通道级消融定位 silent bug**：混合检索实为单通道被 RRF 静默掩盖，通过 `SELECT count(*)` + freelist 分析定位根因，补通道健康断言防止再犯。
2. **query 构造与数据集形态匹配**：全 AND 在长问句 benchmark 上被废，但短查询反而好，用消融实验量化"泛化性是双向的"。
3. **扰动集建泛化门槛**：不唯 benchmark，用去术语化/短查询/跨语言三类变体量化"换个人换个问法，系统还稳不稳"，这是工程级 RAG 的必备能力。
4. **双层修复（检索+生成）从跑分定位短板**：semantic 26.7% → query 改写；constrained 0/11 → prompt 覆盖子项，benchmark 驱动的分层优化。

这些都是"我不只是跑了个分，我建了个可复现、可验证、有泛化保障的评测体系"的硬证据。

## 五、实测结果（2026-09-19，era-2，官方数字）

> 评测语料为修复后全量重导（v3）：BM25 索引 130,303 行（era-1 残缺语料仅 73,171 行）。
> 每轮 64 题，Judge=GLM-5.3（openai_compatible），判分日志已 `grep APIConnectionError` 确认零网络污染。

### 5.1 六轮消融总表

| 轮次 | 配置 | Recall | Completeness | Correctness | 答对 |
|---|---|---|---|---|---|
| r01 | hybrid 基线 | 61.71% | 44.04% | 26.56% | 17/64 |
| r02 | 纯向量 | 49.48% | 43.71% | 25.00% | 16/64 |
| r03 | 纯 BM25 | 57.08% | 32.68% | 20.31% | 13/64 |
| r04 | hybrid + 改写 | 61.00% | 41.43% | 26.56% | 17/64 |
| r05 | hybrid + HyDE | **65.89%** | 49.91% | 34.38% | 22/64 |
| r06 | hybrid + 改写 + HyDE（全开） | **66.20%** | **50.53%** | **35.94%** | **23/64** |

### 5.2 结论与验收

- **对比初始基线**（9/16，BM25 修复前 + 残缺语料）：Recall 48.37% → 66.20%（+17.8pp），Correctness 14.06% → 35.94%（+21.9pp），答对 9/64 → 23/64。
- **三条验收线全部达标**：recall ≥ 55 ✅（66.20）、correctness ≥ 25 ✅（35.94）、semantic recall ≥ 40 ✅（r06 达 53%）。
- **通道消融复现且增强**：hybrid（61.71）比最强单通道 BM25（57.08）+4.6pp，RRF 融合确实带来增量；纯 BM25 仍强于纯向量，验证 BM25 修复有效。
- **HyDE 是最大单项增益**：vs r01，correctness +7.8pp（26.56 → 34.38），completeness +5.9pp。
- **Query 改写单独无增益**（r04 ≈ r01），但与 HyDE 叠加后 r06 仍比 r05 高，保留为可配置项。
- **constrained 题型**：correctness 0 → 27.27%（3/11），prompt 去保守化见效，但仍是最大生成层短板。
